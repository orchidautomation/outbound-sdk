An adapter is the part that knows one vendor. It describes each request and maps the response to the SDK's records. It never retries, sleeps or walks pages: `createOutbound` does that around it, the same way for every vendor. You pass one adapter to `createOutbound` and call the same methods whichever vendor is behind it (see [usage](/docs/usage)).

Each vendor adapter has two layers: normalized reads that mean the same thing on every vendor, and a typed [native catalog](/docs/native) of the vendor's own reads for everything else.

## The adapters

| Adapter | Import | Channel | Key variable | Page |
| --- | --- | --- | --- | --- |
| Instantly (API V2) | `outbound-sdk/instantly` | email | `INSTANTLY_API_KEY` | [Instantly](/docs/adapters/instantly) |
| Smartlead | `outbound-sdk/smartlead` | email | `SMARTLEAD_API_KEY` | [Smartlead](/docs/adapters/smartlead) |
| HeyReach | `outbound-sdk/heyreach` | LinkedIn | `HEYREACH_API_KEY` | [HeyReach](/docs/adapters/heyreach) |
| EmailBison | `outbound-sdk/emailbison` | email | `EMAILBISON_API_KEY` | [EmailBison](/docs/adapters/emailbison) |
| In-memory | `outbound-sdk/memory` | both | none | [In-memory](/docs/adapters/memory) |

[`combine`](/docs/adapters/combine) from `outbound-sdk/combine` puts several of them, or several keys for one of them, behind one instance.

Every vendor factory takes the same core options:

| Option | Default | What it is |
| --- | --- | --- |
| `apiKey` | the key variable above | The vendor key. A missing key throws when the adapter is constructed. |
| `workspaceId` | `<PROVIDER>_WORKSPACE_ID`, then `default` | Your own label for the client or workspace. It is part of every ref (`provider:workspace:id`). |
| `baseUrl` | the vendor's API | For a proxy or a test server. |
| `leadFields` | none | Which of a lead's custom fields holds a value the vendor has no field for, such as `{ title: "job_title" }`. Read only where the vendor's own field is empty. See [field grades](/docs/capabilities#field-grades). |
| `capabilities` | what the adapter declares | Overrides single capabilities, for example to turn one off on a plan without the endpoint. |

Constructing an adapter makes no request.

## How far each is verified

One line each, from [what is verified](/docs/status), which is the page to read before relying on a number:

- **Instantly** is `beta`: its reads were run, read-only, against one live workspace on 2026-11-14.
- **HeyReach** is `beta`: its reads were run, read-only, against one live workspace on 2026-11-14.
- **Smartlead** is `unverified`: written from Smartlead's public documentation and tested offline only.
- **EmailBison** is `unverified`: written from EmailBison's API reference and tested offline only. No EmailBison account is available to the project.
- **In-memory** is `stable`: it has no vendor behind it.

`outbound.maturity` reports this at run time, and `outbound.caveats` lists what the adapter assumes and has not confirmed. Each adapter's page shows its caveats in full.

## What stays `no`, and why

What a vendor's API cannot answer stays `no`. The SDK does not fill the gap with a guess.

- **HeyReach has no campaign settings, subsequences, tags or per-lead counts.** Its API can set a campaign's schedule but not read it, a campaign has one sequence tree, no endpoint lists the workspace's tags, and no lead carries open or reply counts.
- **HeyReach has no per-step stats**, no warmup and no inbox placement tests: LinkedIn accounts are not warmed up and have no inbox to test.
- **Smartlead and HeyReach have no endpoint that lists every lead.** `leads.list` is `yes` because each adapter walks the campaigns and reads their leads. A lead in no campaign is never returned.
- **On Smartlead and HeyReach a reply's category is its lead's.** Neither vendor labels a message. The reply carries `categorySource: "lead"` to say so, and `outbound.fields.reply.category` is `derived`.
- **HeyReach cannot list workspaces** with a workspace key.
- **Smartlead cannot list the leads of a saved list**, and its per-lead counts are documented only as a placeholder response.
- **Instantly's per-mailbox stats are `derived`:** its mailbox analytics exist per day only, so the adapter sums them.
- **EmailBison has no campaign progress, follow-up sequences, row per campaign or placement tests**, and no read returns the leads of a lead list.
- **No adapter reveals deleted records.** The [reconcile plugin](/docs/plugins/reconcile) compares what you stored with what the vendor still lists.

## How much of each vendor's API is covered

Every endpoint in each vendor's API reference is listed on its [coverage](/docs/coverage) page with how the SDK reaches it: through a normalized read, through the native catalog, excluded with a reason, or a write the SDK does not make.

| Vendor | Endpoints | Normalized | Native | Excluded | Writes |
| --- | --- | --- | --- | --- | --- |
| [Instantly](/docs/coverage/instantly) | 268 | 22 | 105 | 4 | 137 |
| [Smartlead](/docs/coverage/smartlead) | 230 | 27 | 78 | 20 | 105 |
| [HeyReach](/docs/coverage/heyreach) | 106 | 17 | 25 | 3 | 61 |
| [EmailBison](/docs/coverage/emailbison) | 180 | 28 | 32 | 5 | 115 |

A read is excluded only when it returns secrets (API keys, mailbox passwords, proxy credentials), duplicates another endpoint's data exactly, reports nothing about campaigns, leads, senders or results (billing, marketplace pricing, search filter lists), or returns a file the SDK cannot carry. Reads that spend vendor credits are listed as writes.

## Rate limits each adapter declares

| Adapter | Declared limit | Stricter lanes |
| --- | --- | --- |
| Instantly | 100 per second and 6,000 per minute, per workspace | `GET /emails`: 20 per minute |
| Smartlead | 60 per minute (the limit of a client key; an admin key is documented at 200) | three endpoints at 10 per minute |
| HeyReach | 15 per 2 seconds (seen live, not documented) and 300 per minute | the organization API: 300 per minute |
| EmailBison | 3,000 per minute (from a marketing page; the reference documents none) | none |

The SDK spends `share` (default 0.5) of these numbers, because the vendor's limit is shared with the customer's other tools. [Rate limits](/docs/rate-limits) explains the budget, and [what is verified](/docs/status) says which of these numbers were measured.

## The provider catalog and choosing an adapter at run time

`outbound-sdk/providers` lists every provider with its channels, its maturity and the environment variables it reads, without importing any adapter. `outbound-sdk/loader` builds the adapter that `OUTBOUND_SDK_PROVIDER` names, reading that adapter's own key from the environment; the [CLI](/docs/cli) and `outbound mcp` pick their adapter this way.

Set it to `all`, or call `fromEnv({ provider: "all" })`, to build every provider whose required key is set. With `OUTBOUND_SDK_PROVIDER` not set and no `provider` passed, `fromEnv()` does the same. One key gives that adapter alone; several give one [combined](/docs/adapters/combine) instance, in catalog order. `configuredProviders()` returns the ids it would build. `isProviderId(value)` from `outbound-sdk/providers` says whether a string, such as a `--provider` flag, is an id in the catalog, and narrows it to the `ProviderId` type. A provider that needs no key, `memory`, is never included, and with no key set the call throws `Invalid` and names the variables. A combined instance promises only what all its members can do, so adding a key can remove a capability: see [what it promises](/docs/adapters/combine).
