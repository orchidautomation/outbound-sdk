`outbound-sdk/tools` gives an agent tools shaped like the questions an operator asks: how are my campaigns doing, which step gets replies, which senders need attention. Your model does the reasoning. A tool only reads from the vendor and arranges what it read. The SDK calls no model.

Every tool:

- **Takes one JSON object** and describes it as JSON Schema, so any model API can call it.
- **Returns compact JSON** with `data`, `meta` and `next`. `meta.evidence` says how far to trust the numbers (`exact`, `sampled` or `derived`), `meta.requests` how many vendor requests the call made, `meta.today` is today's date in UTC (a model does not know it, and otherwise guesses the date range it asks for), `meta.complete` is `false` when the answer covers part of what was asked, with `meta.notes` saying why, and `next` suggests what to ask after this. Every tool, built-in or insight, reports coverage in `meta.complete` and `meta.notes` and nowhere else. `outbound tool` prints the result in [the CLI's envelope](/docs/cli#the-envelope).
- **Never throws.** Bad input, a missing record and a read the adapter cannot serve all come back as `{ ok: false, error, next }`, which a model can read and recover from.
- **Only reads.** No tool sends, pauses or edits anything.

This page uses the [in-memory adapter](/docs/adapters/memory). How far each real adapter has been checked is on [what is verified](/docs/status).

## The twelve tools

| Tool | Answers | Needs |
| --- | --- | --- |
| `campaign_overview` | How every campaign with a given status is doing | `campaigns.status`, `stats.campaign` |
| `campaign_trend` | How one count moved day by day for a campaign, over the last 30 days unless `from` or `to` is given | `stats.campaign`, `stats.byDay` |
| `winning_steps` | Which step or variant drives replies, ranked by reply rate (`rank`), each with `step_index` (from 0) and `step_number` (from 1); counts tied to no step come last as `unattributed`. `step` is a deprecated copy of `step_index`, removed in 0.8.0 | `stats.byStep` |
| `sender_health` | Status, daily limit and warmup per sender, unhealthy first | `senders.list` |
| `reply_samples` | Recent replies, optionally by category | `replies.list` |
| `lead_runway` | Days until a campaign has no new leads left to start, at the pace of new leads started. An estimate. | `leads.byCampaign`, `stats.campaign`, `stats.byDay` |
| `compare_clients` | The same counts for every client, side by side | the [`clients` plugin](/docs/plugins/clients), `stats.campaign` |
| `cross_channel_lead` | Every record and message for one person | the [`identity` plugin](/docs/plugins/identity) |
| `campaign_setup` | How one campaign is set up to send: windows, caps, tracking, stop rules | `campaigns.settings` |
| `deliverability_check` | Each sender's DNS records, sign-in state and warmup spam rate, problems first | `senders.health` |
| `audience_lists` | The saved lead lists and their sizes | `lists.list` |
| `vendor_read` | Anything else the vendor reports: lists the vendor's own reads, then runs one | a [native](/docs/native) catalog |

The last column is the tool's own `needs`: the [capabilities](/docs/capabilities) and plugins it cannot work without. `createTools` reads it to decide what to offer.

`needs` lists only what every call makes use of. An input can ask for more: `reply_samples` with `category` also needs `replies.category`, `deliverability_check` needs `senders.list`, or with `campaign` `senders.byCampaign`, and `cross_channel_lead` reads a timeline only when the adapter declares `leads.timeline`.

## When a list is cut

`campaign_overview`, `sender_health`, `reply_samples` and `audience_lists` return at most `limit` rows. Each sets `meta.complete` to `false` when more exist than it returned, with a note such as "Stopped at 10 campaigns (limit); more active campaigns exist.", and its card shows the note.

`sender_health` counts problems over more senders than it lists: at least the first 100, or `limit` when that is larger, which is one vendor page and so costs no extra request. `data.unhealthy` counts the paused, disconnected and failing senders among the `data.checked` senders, and they are listed first. `meta.complete` is `false` when the account has more senders than were checked, or when `limit` left checked senders out of the list, and `meta.notes` says which.

`deliverability_check` screens every sender, up to 500, from the sender list for a disconnected or failing status and a warmup score of 0, then checks the first `limit` in full, those with a problem first. `data.with_problems` counts problems across every screened sender. `data.checked` is how many were checked in full and `data.total` how many senders there are, or `null` past 500. `meta.complete` is `false` when not every sender was checked in full, and `meta.notes` says how many were and whether more than 500 exist.

## What is left out, and what is refused

Two different things happen when a tool cannot work.

**Left out of the set.** `createTools` does not offer:

- A tool that needs a capability the adapter lacks, or that a plugin turned off.
- `compare_clients` without the `clients` plugin on the instance.
- `cross_channel_lead` without the `identity` plugin, or while the [`redact` plugin](/docs/plugins/redact) masks `email` or `linkedin`, because `outbound.person()` is refused then.
- `vendor_read` when the adapter has no native reads, or when the `redact` plugin is on the instance, because a native read returns the vendor's payload untouched.

A tool's `next` hint never names a tool that is not in the set. When the hint a tool wrote would, it is replaced by a general one.

**Offered, then refused.** A tool in the set can still be asked for a read only its input needs. Calling it then returns `{ ok: false }` with the code `Unsupported` and a `next` hint that tells the model to try another tool.

## When a tool fails

<include meta='title="failures.ts"'>
  ../../_examples/tools-index/failures.ts
</include>

<include lang="text" meta='title="Output"'>
  ../../_examples/tools-index/failures.out.txt
</include>

| What happened | `error.code` | What the model is told |
| --- | --- | --- |
| An argument the tool does not take | `Invalid` | The stray key and the inputs the tool takes |
| A value of the wrong type or shape | `Invalid` | The field and what was wrong with it |
| A record that does not exist | `NotFound` | Which record |
| A read the adapter or a plugin does not allow | `Unsupported` | Which capability is missing, and to try another tool |
| The call reached its [request cap](#request-caps) | `RateLimited` | Not to call again with the same input: the input to lower, when one would fit, or to ask the user to raise `maxRequestsPerToolCall`. `meta.requests` says what it spent. |
| A `budget()` or `maxRequestsPerCall` cap the user set | `RateLimited` | That a cap the user set was reached, and not to call again with the same input |
| The vendor's rate limit, past the SDK's retries | `RateLimited` | To wait a minute before calling again |
| Anything that is not an `OutboundError` | `Provider` | The error's message |

Every failure has `error.retryable`: `false` when the same call would fail the same way again (bad input, a missing record, a read that is not allowed, a cap of your own), `true` when it may work later (the vendor's rate limit or an outage). A cap stop is never retryable, so a model is not invited to loop on it.

Input is strict. An argument a tool does not take is reported as `Invalid`, never dropped, so a model that invents a filter learns that the filter did nothing. The other codes are the ones on the [errors](/docs/api/errors) page.

## Add the insights

The 26 [insights](/docs/insights) are tools of the same shape. `insightTools(outbound)` from `outbound-sdk/insights` returns the ones the adapter can serve, and the `extra` option of `createTools` and of every wrapper appends them.

</include>

An insight tool returns the insight's answer as its `data`, and says how much it covers in `meta.complete` and `meta.notes`, as the built-in tools do. The insight's answer keeps its own camelCase keys, as every insight's answer does wherever it is read (see [names](/docs/insights#names)), so `step_funnel` returns `replyRate` while `winning_steps` returns `reply_rate`. Like the twelve built-in tools, an insight whose adapter lacks a capability it needs is left out of the list.

## Options

| Option | What it does |
| --- | --- |
| `only` | Offer only these built-in tools, by name. Defaults to every tool the instance can serve. |
| `extra` | More tools to offer after the built-in ones. `only` does not filter them. |
| `maxRequestsPerToolCall` | The most vendor requests one tool call may send, retries included. Applies to the built-in tools and is passed to each `extra` tool's `call`. See below. |

## Request caps

Each tool call gets a fresh allowance of vendor requests, counted across every read the call makes, including reads that run side by side. A model calling tools in a loop therefore cannot spend a vendor's quota on one question, and you do not have to add [`budget()`](/docs/plugins/budget) to get that.

| Tool | Default allowance per call |
| --- | --- |
| A built-in tool | 100 requests (`DEFAULT_TOOL_REQUESTS`) |
| An [insight tool](/docs/insights#request-caps) | What its input can cost, a quarter more for retries and 4 on top, but never more than 500 (`INSIGHT_TOOL_CEILING`) |

The 500 ceiling keeps a model from buying itself a larger allowance by raising a `max_*` input. `maxRequestsPerToolCall` on `createTools` (or on `insightTools`) replaces the default; `Infinity` removes it. A `maxRequestsPerCall` on the instance and a `budget()` still apply under it, and the lowest cap stops the call. A caller can also pass `{ maxRequests }` as the second argument of one tool's `call`.

A call that reaches its allowance stops before the next request and returns `ok: false` with `RateLimited`, `retryable: false`, `meta.requests` and a `next` such as `Do not call again with the same input. Lower max_campaigns to 13, or ask the user to raise maxRequestsPerToolCall (default 287 here).` An insight tool that cannot fit is refused before it spends anything; see [insights](/docs/insights#request-caps).

## Reply text

Each record `reply_samples` returns is one message, not one person, and its description tells the model so. `data.unique_people` and `data.unique_threads` count the people and threads behind the replies, or are `null` when a reply has no lead or thread. With `by: "person"` it returns `data.people`, one row per person with their `messages`, `first_at`, `last_at`, `categories` and `thread_ids`, in place of `data.replies`.

`reply_samples` leaves reply text out unless the model asks for it, and marks it as untrusted when it does. Read [untrusted content](/docs/tools/untrusted-content) before you let a model read replies.
