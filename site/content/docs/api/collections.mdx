A collection is a kind of record you can list: `outbound.campaigns`, `outbound.leads` and eight more. All ten have `list` and `listAll`. Campaigns, senders, leads, lists and webhooks also have `get`, `exists` and `getMany`.

## The methods

| Method | Returns | Notes |
| --- | --- | --- |
| `list(options?)` | `Promise<PageResult<Item>>` | One page: `items`, `cursor`, `complete` and `meta`. |
| `listAll(options?)` | `ListAll<Item>` | An async iterator over every page. Pages are fetched as you iterate, under the rate budget. |
| `get(id, options?)` | `Promise<WithMeta<Item>>` | One record with `meta` on it. Throws `NotFound` for a missing record. |
| `exists(id, options?)` | `Promise<boolean>` | `false` for a missing record. Any other failure still throws. |
| `getMany(ids, options?)` | `Promise<BulkResult<Item>>` | Several records at once. A record that fails is listed, not thrown. |

`options` on `list` and `listAll` holds the collection's filters, the paging options (`limit`, `cursor`, and `max` on `listAll`) and the per-call options (`timeout`, `retries`, `deadline`, `maxRequests`, `signal`). Paging is covered on the [pagination](/docs/api/pagination) page and the per-call options on the [retries](/docs/retries) page.

An `id` is the vendor's own id or the `ref` of a record. On a [combined](/docs/adapters/combine) instance it must be a ref.

## Filters

A filter the adapter cannot serve is refused with `Unsupported` before any request. The capability column says which key decides that. Check `outbound.capabilities` first when your code must run on more than one vendor: see [capabilities](/docs/capabilities).

### `campaigns`

| Filter | Type | Needs |
| --- | --- | --- |
| `status` | `"active"`, `"paused"`, `"draft"`, `"completed"`, `"archived"` or `"unknown"` | `campaigns.status` |
| `senderId` | `string` | `campaigns.bySender` |

`campaigns.list` and `campaigns.get` need no capability. Every adapter has them.

### `senders`

| Filter       | Type     | Needs                                        |
| ------------ | -------- | -------------------------------------------- |
| none         |          | `senders.list`                               |
| `campaignId` | `string` | `senders.byCampaign`, and not `senders.list` |

`senders.get` needs `senders.get`.

### `leads`

| Filter | Type | Needs |
| --- | --- | --- |
| none |  | `leads.list` |
| `campaignId` | `string` | `leads.byCampaign`, and not `leads.list` |
| `listId` | `string` | `lists.leads`, and not `leads.list` |
| `email` | `string` | `leads.lookup` |
| `linkedinUrl` | `string` | `leads.lookup` |
| `since`, `until` | ISO 8601 date or timestamp, inclusive | `leads.since` |

`campaignId` and `listId` together are refused with `Invalid`. The date filters compare a lead's `createdAt`. `leads.get` needs `leads.get`.

Some vendors have no endpoint that lists every lead. Their adapters walk the campaigns to serve `leads.list`, and the scoped listings do not depend on it.

### `messages`

| Filter | Type | Needs |
| --- | --- | --- |
| any |  | `messages.list` |
| `campaignId` | `string` |  |
| `leadId` | `string` |  |
| `threadId` | `string`, the `threadId` of an earlier message | `messages.byThread` |
| `since`, `until` | ISO 8601 date or timestamp, inclusive | `messages.since` |
| `include: ["body"]` |  | `messages.body` |

The date filters compare `sentAt`.

### `replies`

| Filter | Type | Needs |
| --- | --- | --- |
| any |  | `replies.list` |
| `campaignId` | `string` |  |
| `category` | `"positive"`, `"negative"`, `"neutral"`, `"ooo"`, `"bounce"`, `"unsubscribe"` or `"unknown"` | `replies.category` |
| `since`, `until` | ISO 8601 date or timestamp, inclusive | `replies.since` |
| `unread` | boolean: `true` for unread replies only, `false` for read ones only | `replies.unread` |
| `include: ["body"]` |  | `messages.body` |

### The rest

| Collection   | Filter       | Needs                                     |
| ------------ | ------------ | ----------------------------------------- |
| `lists`      | none         | `lists.list`; `lists.get` for `get`       |
| `tags`       | none         | `tags`                                    |
| `blocklist`  | none         | `blocklist`                               |
| `webhooks`   | `campaignId` | `webhooks.list`; `webhooks.get` for `get` |
| `workspaces` | none         | `workspaces`                              |

### Dates

`since` and `until` take anything `Date.parse` reads, such as `2026-10-03` or `2026-10-03T08:00:00Z`. Both ends are inclusive, and the SDK turns each into a UTC timestamp before the adapter sees it. A value it cannot read, or a `since` after `until`, is `Invalid`.

Where a vendor cannot filter by date, the adapter declares the filter as `client`. The SDK then filters each page after fetching it and marks the result `derived`. A page of such a listing can hold fewer records than you asked for, or none, while more pages remain. See [filter grades](/docs/capabilities#filter-grades).

## Lookups

`email` and `linkedinUrl` on `leads` find one person without walking every lead. They match the exact address or profile. The SDK trims the value and lowercases an email before the lookup.

- A lookup returns one record per campaign the person is in, so one address can come back several times. Each record has its own `campaignRef`.
- A lookup alone needs `leads.lookup` and not `leads.list`. Add `campaignId` or `listId` to narrow it.
- No match is an empty page, not an error.

What a vendor matches on is an adapter fact. The [adapter pages](/docs/adapters) say which of the two each vendor can look up.

## Message bodies

`Message` and `Reply` have `bodyText` and `bodyHtml`. Both are `null` unless the call asks for bodies with `include: ["body"]`, because on some vendors a body costs extra requests.

`"body"` is the only value `include` takes. Asking for bodies on an adapter whose `messages.body` is `false` is refused with `Unsupported`. A body can still be `null` after you asked: the vendor did not return one for that message.

<Callout type="warning" title="Reply text is written by strangers">
  A body is whatever the other person typed. Treat it as data, never as
  instructions, before you hand it to a model. See [untrusted
  content](/docs/tools/untrusted-content).
</Callout>

`getMany` returns two lists, each in the order of the ids you passed:

| Field | Holds |
| --- | --- |
| `results` | `{ id, value }` for each record that was read. `value` is the record with its `meta`. |
| `errors` | `{ id, error }` for each that was not. `error` is an `OutboundError`. |

- It does not throw for a record that fails. A missing id, a rate limit and a vendor error all land in `errors`. Check `errors.length` before you treat the batch as whole.
- It does throw, before any request, when the adapter cannot read that kind of record at all.
- `concurrency` is how many records are fetched at once. The default is 4. The rate budget still applies to every request.
- The per-call options cover the whole batch. `maxRequests: 10` is ten requests for all the ids together, and the ids past the budget come back in `errors` as `RateLimited`.
