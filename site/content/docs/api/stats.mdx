Stats are counts: how many were sent, opened, replied, bounced. The SDK returns counts only and computes every rate from them with one set of definitions, so a reply rate means the same thing on every vendor. A vendor's own percentages are never passed through.

## Three ways in

| Call | Scope |
| --- | --- |
| `outbound.stats(options?)` | The workspace by default, or any scope with `scope` and `scopeId` |
| `outbound.campaign(id).stats(options?)` | That campaign, or its steps with `scope: "step"` |
| `outbound.sender(id).stats(options?)` | That sender |

All three return a `StatsResult`: `rows`, an array of [`MetricRow`](#the-counts), and [`meta`](/docs/api/results).

## Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `scope` | `"workspace"`, `"campaign"`, `"step"`, `"sender"` | `"workspace"` | What the counts are for. On `campaign(id).stats` only `"campaign"` (the default) and `"step"`. Not an option on `sender(id).stats`. |
| `scopeId` | `string` | none | The campaign for the `campaign` and `step` scopes, the sender for `sender`. Only on `outbound.stats`: the handles fill it in. |
| `scopeIds` | `string[]` | none | Several senders for the `sender` scope, in place of `scopeId`. Only on `outbound.stats`. |
| `from` | `YYYY-MM-DD` | none | First day, inclusive. |
| `to` | `YYYY-MM-DD` | none | Last day, inclusive. |
| `by` | `"total"` or `"day"` | `"total"` | One row over the range, or one row per day. |

Plus the per-call options every read takes: see [retries](/docs/retries).

- `from` and `to` are calendar days, not timestamps. Anything else, such as `2026-11-09T00:00:00Z`, is `Invalid`. So is a `from` after `to`, and the `step` scope without a `scopeId`.
- `scope: "campaign"` without a `scopeId` returns one row per campaign from a single vendor request, each with the campaign's `scopeRef`. Instantly and Smartlead serve it as totals only; `by: "day"` there is `Unsupported`.
- With no `from` or `to`, the SDK passes no range and the adapter decides what the vendor is asked for. Pass both when the number matters.
- `scope: "step"` returns one row per step, each with its `stepIndex`.
- `scope: "sender"` with `scopeIds` returns each sender's rows from one read where the vendor allows it, each with that sender's `scopeRef`. Instantly reads up to 200 mailboxes a request. `scopeIds` on another scope, beside `scopeId`, or empty is `Invalid`.
- `scope: "sender"` with neither `scopeId` nor `scopeIds` lists every sender, then reads them as `scopeIds` does: on Instantly, 303 senders cost 4 listing pages and 2 daily reads, plus the tracking lookup. `meta.requests` counts the listing, and a note says how many senders were listed. Where the adapter cannot read several senders at once, it is `Unsupported` before any request; pass a `scopeId` per sender instead.
- A scope with nothing to report returns no rows. An empty `rows` is not a row of zeros.

## Scopes and capabilities

Each scope needs a capability, and `by: "day"` needs one more. A scope the adapter cannot serve is refused with `Unsupported` before any request.

| Request | Needs |
| --- | --- |
| `scope: "workspace"` | `stats.workspace` |
| `scope: "campaign"` | `stats.campaign` |
| `scope: "campaign"`, no `scopeId` | `stats.allCampaigns` |
| `scope: "step"` | `stats.byStep` |
| `scope: "sender"` | `stats.bySender` |
| `scope: "sender"`, `scopeIds` | `stats.bySenders` as well |
| `scope: "sender"`, no `scopeId` | `stats.bySenders` and `senders.list` as well |
| `by: "day"`, on any scope | `stats.byDay` as well |

### Grades

A stat capability is `"exact"`, `"derived"` or `false`.

| Grade | Meaning |
| --- | --- |
| `exact` | The vendor reports these counts for this scope, and the adapter passes them on. |
| `derived` | The adapter computes them from other vendor data, for example by adding up daily rows. |
| `false` | Not available. |

Each row says which it was in its own `evidence` field, and `meta.evidence` is `derived` as soon as one row is not `exact`. The [adapter pages](/docs/adapters) list each vendor's grades.

## The counts

Every count on a `MetricRow` is a non-negative number, or `null` when the vendor does not report it. See [null is not zero](/docs/api/records#null-is-not-zero).

| Field | Counts |
| --- | --- |
| `sent` | Messages sent: email sends, or LinkedIn messages. |
| `delivered` | Messages delivered. |
| `contacted` | Unique leads contacted. |
| `opened` | Unique opens. `null` when the campaigns behind the row did not measure opens; see [opens and clicks that were not measured](#opens-and-clicks-that-were-not-measured). |
| `openedTotal` | Every open, repeats included. |
| `clicked` | Unique clicks: leads who clicked at least once. `null` when they were not measured, like `opened`. |
| `clickedTotal` | Every click, repeats included. |
| `replied` | People who replied, each counted once however many replies they sent. Auto-replies are counted in `repliedAuto` where the vendor separates them. |
| `repliedAuto` | People whose replies were automatic. |
| `repliedTotal` | Reply messages from people, every reply counted: a lead who replied twice counts 2. Optional. |
| `repliedAutoTotal` | Automatic reply messages, every one counted. Optional. |
| `positive` | People the vendor marked positive. |
| `bounced` | Messages that bounced. |
| `unsubscribed` | Unsubscribes. |
| `connectionsSent` | LinkedIn connection requests sent. LinkedIn only. |
| `connectionsAccepted` | LinkedIn connection requests accepted. LinkedIn only. |
| `inmailsSent` | LinkedIn InMails sent. LinkedIn only. |
| `leads` | Leads in the campaign now, whatever their progress. Optional. |
| `completed` | Leads who reached the end of the sequence. Optional. |
| `meetingsBooked` | Meetings booked: leads the vendor moved to its meeting-booked status in the range. Never opportunities or positive replies. Optional. |
| `opportunities` | Opportunities the vendor counts for the leads. Optional. |
| `opportunityValue` | What those opportunities are worth, in the vendor workspace's own currency. Optional. |

`replied` counts people and `repliedTotal` counts messages, the way `opened` and `openedTotal` do. Instantly's dashboard shows "Unique replies", which is `replied`, and "Replies", which is `repliedTotal` plus `repliedAutoTotal`. A [`Reply`](/docs/api/records#reply) record is one message, so a list of replies can be longer than `replied`. Today only Instantly fills `repliedTotal` and `repliedAutoTotal`; every other adapter sets them to `null`.

`leads`, `completed`, `meetingsBooked`, `opportunities` and `opportunityValue` are optional: a row may leave them out, and the adapters in this package set them to `null` where the vendor does not report them. Today only Instantly fills them, on campaign and workspace totals; `leads` is only on the rows of `stats({ scope: "campaign" })`, and `meetingsBooked` only on one campaign's total and the workspace total, which Instantly reads from its analytics overview. `outbound.fields.metricRow.meetingsBooked` is `false` on a tool that records no meetings, so a `null` there means the tool has none to give, not that nobody booked one. `contacted` can be a little over `leads`, because a lead removed after its sequence started is still counted as contacted.

The other fields say what the row is:

| Field | Type | Holds |
| --- | --- | --- |
| `scope` | `"workspace"`, `"campaign"`, `"step"`, `"sender"` |  |
| `scopeRef` | `string` | The ref of the campaign or sender the row is for. |
| `date` | `YYYY-MM-DD` or `null` | The day, for a daily row. `null` for a total. |
| `timezone` | `string` or `null` | The vendor's timezone for a daily row: `"UTC"` on Instantly and HeyReach, `null` where the vendor does not say. A vendor's "day" is not always UTC. |
| `stepIndex` | integer or `null` | The step, for a per-step row. |
| `variantKey` | `string` or `null` | The variant, for a per-variant row. |
| `contentHash` | `string` or `null` | The hash of the copy the row is for, where known. |
| `evidence` | `"exact"`, `"derived"`, `"sampled"` | How this row was obtained. |
| `tracking` | `{ opens, clicks }`, each `"on"`, `"off"`, `"mixed"` or `null`. Optional | The open and click tracking of the campaigns behind the row, as their settings are now. `mixed` means some track and some do not; `null` that a setting is unknown. Absent when the adapter did not read the settings. |
| `provider`, `workspaceId`, `schemaVersion` |  | As on every [record](/docs/api/records). |

## Opens and clicks that were not measured

A campaign with open or link tracking off records no opens or clicks, so its 0 would read as "nobody opened". An open or click count is a number only when every campaign behind the row measured it; otherwise it is `null`, and `tracking` says why. Opens and clicks are decided separately.

- **One campaign** (its total, its days or its steps). With tracking off and no opens in the whole range, `opened` and `openedTotal` are `null` on every row, so a daily series never mixes 0 and `null`. With tracking off but opens in the range, the numbers stand: vendors report only the current setting, so those opens were recorded while tracking was on. `tracking.opens` is `"off"` either way. Clicks follow the same rule with `clicked` and `clickedTotal`.
- **Mixed tracking.** A workspace, sender or other total over several campaigns judges each campaign that sent in the range. When every one measured opens, the vendor's number stands. When any did not, the count is `null` and `tracking.opens` is `"off"` or `"mixed"`, never a sum of the tracked campaigns alone: that sum divided by every send would understate the open rate without saying so. For the tracked part, read `stats({ scope: "campaign" })`, which returns a row per campaign, each judged on its own.
- **Unknown settings.** When the settings cannot be read, or a flag is not reported, the counts are as the vendor sent them and `tracking` is absent or `null`.

Reading the settings costs extra requests: one for a campaign, and the per-campaign report plus the campaign listing for a workspace or sender total. Each [adapter page](/docs/adapters) lists them. HeyReach has no tracking, and EmailBison has no click setting, so its `tracking.clicks` is `null`.

What a vendor counts as an open or a reply differs in the details. Each adapter's `caveats` and its [adapter page](/docs/adapters) record what is known.

## Rates

`computeRates(row)` returns six rates for one row. Each is `{ value, basis }`: `value` between 0 and 1, and `basis` the count it was divided by.

| Rate | Numerator | Divided by |
| --- | --- | --- |
| `replyRate` | `replied` | `contacted`, or `sent` when `contacted` is missing |
| `positiveReplyRate` | `positive` | `contacted`, or `sent` |
| `unsubscribeRate` | `unsubscribed` | `contacted`, or `sent` |
| `openRate` | `opened` | `delivered`, or `sent` when `delivered` is missing |
| `bounceRate` | `bounced` | `sent` |
| `acceptanceRate` | `connectionsAccepted` | `connectionsSent` |

- A rate is `{ value: null, basis: null }` when its numerator is missing, or when every base it could use is missing or 0. The sample has no LinkedIn counts, so `acceptanceRate` is `null`.
- Read `basis` before comparing two rates. A reply rate over `contacted` and one over `sent` are different numbers for the same campaign.
- An open rate is `null` when opens were not measured (see above). Where it exists, mail privacy features inflate it.

`METRIC_DEFINITIONS` holds a `name` and a one-sentence `description` for each rate, keyed by the same six names. Use them as labels and tooltips so a report says what its numbers mean.

## Adding rows

`sumCounts(rows)` adds rows of counts together. A count stays `null` only when no row reports it. `emptyCounts()` is a row with every count `null`.

Unique counts (`opened`, `contacted`) are summed as they are, which over-counts a person who appears in more than one row. A total from the vendor (`by: "total"`) is the better number when the vendor has one.

## Days with no row

A vendor can leave a day out of `by: "day"`: Instantly's and HeyReach's campaign days skip a day with no activity. A missing row is not a 0, so a chart or a warehouse table cannot tell it from a day the vendor never reported. `fillDays(rows, { from, to })` returns one row per scope for every day in the range, oldest first, keeping each row the vendor sent as it was. A day it adds has `evidence: "derived"`, its scope's `timezone`, and every count `null`. With `fill: "zero"`, a count the scope's other rows report is 0 on an added day instead, and a count they never report stays `null`, so a vendor that has no opens does not get 0 opens.
