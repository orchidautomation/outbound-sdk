`outbound mcp` starts a Model Context Protocol server on standard input and output. An agent client such as Claude Code, Claude Desktop or Cursor starts it as a child process and can then call the [AI tools](/docs/tools) and the [insights](/docs/insights) against your account.

- **Local.** The server is a process on your machine, started by your client. Nothing is hosted.
- **Stores nothing.** It keeps no state between calls and writes no file.
- **Read-only.** Every tool only reads, and each is listed with `readOnlyHint: true`.
- **Keys from the environment.** The adapter reads its key from an environment variable. The server takes no key as an argument and the protocol never carries one.
- **Masks personal data by default.** It runs with the [`redact`](/docs/plugins/redact) plugin unless you start it with `--no-redact`. See [plugins](#plugins).

## Configure a client

Most clients take a JSON entry with a command, its arguments and its environment. Use the path to the `outbound` binary in the project where you installed the package.

```json
{
  "mcpServers": {
    "outbound": {
      "command": "/path/to/your/project/node_modules/.bin/outbound",
      "args": ["mcp"],
      "env": {
        "OUTBOUND_SDK_PROVIDER": "instantly",
        "INSTANTLY_API_KEY": "your-key"
      }
    }
  }
}
```

To try it with no key, on the demo data:

```json
{
  "mcpServers": {
    "outbound-demo": {
      "command": "/path/to/your/project/node_modules/.bin/outbound",
      "args": ["mcp"],
      "env": { "OUTBOUND_SDK_PROVIDER": "memory" }
    }
  }
}
```

These configurations are not run by the test suite, and no agent client was connected to the server for this page. Where the file lives and what it is called depends on the client; check its documentation. The provider and key variables are the ones on the [CLI overview](/docs/cli#choosing-the-provider).

A key in a client's configuration file is stored in plain text on your disk by that client. A read-only key is enough: the SDK never writes to a vendor.

## Plugins

`outbound mcp` hands your prospects' data to a model, so it runs with [`redact()`](/docs/plugins/redact) unless told not to. Emails, names, companies, LinkedIn URLs, custom fields and message text come back masked, a request for reply text is refused, and `person`'s timeline and account views answer with the masked summary. Other plugins come from flags or from a config file. Add them after `mcp` in the client's `args`:

| Flag | What it does |
| --- | --- |
| `--no-redact` | Turns the default `redact()` off. Records come back unmasked and reply text can be asked for. |
| `--cache <seconds>` | Adds [`cache()`](/docs/plugins/cache): a repeat read within that time makes no vendor request. The cache is in memory and lives as long as the server. |
| `--max-requests <n>` | Adds [`budget()`](/docs/plugins/budget): the most vendor requests one tool call may make. |
| `--config <file>` | Loads plugins from a file. See below. |
| `--tools <names>` | Offers only the tools named, separated by commas, such as `--tools campaigns,sender_health`; a name from the last column of the table below offers the listed tool with only that view or check. Every tool's description and inputs cost the client's context before any call, under 56 KB for all of them with `--provider all`, which a test holds. A name the server cannot offer is refused before it starts. |

Set `OUTBOUND_REDACT_KEY` in the server's `env` to keep each person's token from one session to the next, for example to compare answers across days. It is a secret of at least 32 characters; see [redact's fixed key](/docs/plugins/redact#a-fixed-key) for how to treat it. Without it, tokens change each time the server starts.

The sample runs the real `outbound mcp` three times on the demo data: as it starts by default, with `--no-redact`, and with a config file and both flags. Each time it sends `initialize`, `tools/list` and a call that asks for reply text.

The server's `instructions` end with the plugins that are on, so a model can tell why a field is masked or a tool refuses. ### A config file

For any other plugin, or for a plugin's options, pass `--config` with the path to a file whose default export lists the plugins. `defineConfig` from `outbound-sdk/cli` returns what it is given, so an editor can check the shape.

<include meta='title="outbound.config.ts"'>
  ../../_examples/cli-mcp/outbound.config.ts
</include>

- A `.mjs` or `.js` file works on every supported Node. A `.ts` file needs a Node version that runs TypeScript files directly. A file with no types, like the one above, can be named `.mjs`.
- The path is resolved from the folder the client starts the command in. Use an absolute path.
- The plugins are placed in this order, outermost first: `redact()`, the file's plugins, `cache()` from `--cache`, `budget()` from `--max-requests`, then `identity()`, which the CLI always adds unless the file lists it. To place a cache or a budget elsewhere, list it in the file instead of using its flag.
- A `redact()` in the file replaces the default one, with the options you gave it. Setting `--no-redact` as well is refused.
- The file may also export `rateLimitStore`, the store `createOutbound` takes. A vendor's limit covers the whole workspace, so two terminals, or the CLI and an MCP server, on one key slow each other down; with one shared store, such as [`redisRateLimitStore()`](/docs/guides/shared-rate-budget), they spend one budget instead of drawing 429s from each other.
- The file may also export `leadFields`, the custom fields every tool reads a lead field from where the vendor's own is empty, as each adapter's `leadFields` option takes them. `{ linkedinUrl: ["linkedin_profile", "linkedin_url"] }` gives Instantly leads the LinkedIn profiles an account keeps in custom fields, so `person` with view `timeline` can link them to HeyReach. Without a config file, `OUTBOUND_LEAD_FIELDS` takes the same map as JSON.
- A file that cannot be loaded, has no default export, or exports something other than a list of plugins and a rate limit store stops the command with exit code 1 before the server answers anything.

### Waits on rate limits

A tool call that waits more than 5 seconds on rate limits gets `meta.throttledMs` and a note in `meta.notes` that names the last wait, so a model can tell a slow vendor limit, such as Instantly's 20 list-email requests a minute, from a hang. A failed call gets `meta.throttledMs` alone. A wait longer than 2 seconds also prints one line on standard error, which the protocol leaves free. A wait names the vendor's published limit and, when it is lower, the rate this process keeps to: its share of the limit, halved again after each 429, as in "Instantly's emails rate limit (20 a minute; this process reads up to 10 a minute)".

The flags and `--config` work on the other commands too. Only `outbound mcp` turns `redact()` on by default; elsewhere, add `--redact`.

### A request cap per tool call

`--max-requests` adds `budget({ maxRequests, per: "run" })`. The server resets that budget before each tool call, so the cap is what a single tool call may spend, however many reads the tool makes. A tool that reaches it returns `isError: true` with `RateLimited`. The same holds for a server you build yourself: a `budget({ per: "run" })` on the instance is reset before each tool call.

Without `--max-requests` a tool call still has a cap: the [default of each tool call](/docs/tools#request-caps), 100 requests for a built-in tool and what the input can cost, at most 500, for an insight. `--max-requests` sits beside the built-in tools' default, and the lower one stops the call; for an insight it replaces the default. Cap messages name `--max-requests on outbound mcp`. A stopped call has `retryable: false` and a `next` that tells the model not to call again with the same input. To change the default on a server you build yourself, pass `maxRequestsPerToolCall` to `createMcpServer` and to `insightTools`. Several `checks` in one call share one cap, 100 requests unless one is set, and a check the ones before it left nothing is answered as not run; a check called alone keeps its own default.

### A time budget per tool call

Most agent hosts give up on a tool call after about a minute and keep nothing, while a read on a slow lane, such as `unanswered_replies` on Instantly's emails, can take five. So each tool call has a time budget, 50 seconds by default, counted from when the call arrives. `--time-budget <seconds>` sets another for the server; raise the client's tool timeout with it. A wait on a rate limit that would pass the budget is not started, and a read still under way when it runs out is stopped. An insight then answers with what it read, `meta.complete: false` and a note that names the tool, the budget and how to get the rest: call it again with less to read, or raise `--time-budget on outbound mcp`. A built-in tool returns `isError: true` with `RateLimited` and the same message. Tool calls run one at a time, so a call that waits behind another spends its budget waiting. When the budget had time left and only the vendor's rate window stood in the way, for example right after an earlier call used up Instantly's 20 email reads a minute, the input is fine: the call is answered with `retryable: true`, `error.retryAfterMs`, a message that says when the window frees, and a `next` to call again with the same input then.

A client that sends `_meta.progressToken` with `tools/call` gets `notifications/progress` every 5 seconds while the call runs: `progress` is the seconds so far, `total` the budget in seconds, and `message` says how long the call has waited on rate limits and names the last wait. `ping` is answered while a call runs, and `notifications/cancelled` stops the call it names: it reads nothing more and is not answered.

## What the server implements

The protocol is JSON-RPC 2.0, one message per line. The server implements what a tool server needs and nothing else, directly, so the package gains no dependency.

| Method | Answer |
| --- | --- |
| `initialize` | The protocol version, `capabilities.tools`, `serverInfo` and `instructions` |
| `ping` | An empty result |
| `tools/list` | Every tool: `name`, `description`, `inputSchema`, `outputSchema` (the answer envelope) and `annotations.readOnlyHint` |
| `tools/call` | The tool's result once, as `structuredContent`, with a short summary as the `content` text (the whole result as JSON text to a client on a protocol older than `2025-06-18`), and `isError`, with `notifications/progress` first when the call sent a `progressToken` |
| `notifications/cancelled` | Nothing. The call it names stops and is not answered. |
| a notification (no `id`) | Nothing. `notifications/initialized` is accepted and ignored. |
| anything else | Error `-32601`, method not found |

Messages are read while a tool call runs, and each answer is written when it is ready. There are no resources, prompts, sampling or list-change notifications. `PROTOCOL_VERSIONS` lists the protocol versions the server speaks. If the client asks for one of them the server answers with it; otherwise it answers with the newest it has.

## The tools it serves

`outbound mcp` serves the built-in tools the instance can serve, then every insight the adapter can serve. It is built in code with `createMcpServer(outbound, options)` from `outbound-sdk/cli`, which the sample below calls the same way, on an instance with `redact()` as `outbound mcp` starts by default, and drives in-process, with no stdio.

`tools/list` does not list every built-in tool and insight on its own. Neighbours are merged into one tool, so a model picks between fewer tools that do not overlap (OUT-168). A merged tool takes `view`, which runs one of what it is made of, or `checks`, which runs several and answers each under `data.<check>`. It also takes every input of what it is made of; one the chosen view does not take is not used, and a note says so.

| Listed tool | Picked by | Made of |
| --- | --- | --- |
| `campaigns` | `view`: `list`, `ranking`, `trend` | `campaign_overview`, `campaign_ranking`, `campaign_trend` |
| `sender_health` | `checks`: `status`, `deliverability`, `warmup`, `domains`, `bounces` | `sender_health`, `deliverability_check`, `warmup_readiness`, `domain_health`, `bounce_watch` |
| `sender_capacity` | `view`: `capacity`, `load` | `sender_capacity`, `sender_load` |
| `lead_runway` | `view`: `runway`, `forecast` | `lead_runway`, `pipeline_forecast` |
| `list_hygiene` | `checks`: `suppression`, `collisions` | `suppression_check`, `lead_collisions` |
| `copy_review` | `checks`: `audit`, `variants`, `personalization`, `reuse` | `copy_audit`, `variant_test`, `personalization_gaps`, `copy_reuse` |
| `step_funnel` | `view`: `funnel`, `winners` | `step_funnel`, `winning_steps` |
| `person` | `view`: `summary`, `timeline`, `account` | `person_summary`, `cross_channel_lead`, `account_summary` |
| `unanswered_replies` | `include: "thread"` puts each reply's conversation in its item | `dropped_replies`, `thread_context` |

Every other built-in tool and insight is listed as it is, `thread_context` among them. Each listed tool takes `scope`: `provider` and `workspace` read one tool or workspace of `--provider all`, and `tag` reads the campaigns with one tag where the tool can (`client_report`). A scope that names nothing the server reads is refused with what it does read. `initialize` names what the server reads, says once how to read an answer, and points bulk exports to the CLI's `--jsonl` or the SDK.

The names in the last column stopped answering on `tools/call` and `outbound tool` in 0.18.0: a call to one is an unknown tool. Call the listed tool with its `view` or `checks` instead; `initialize` says once which listed tool answers each of them. `--tools` still takes one of them to offer the listed tool with only that view or check. A hint in `next` names tools as they are listed. The SDK's own tools and insights keep their names.

`person` is listed under `redact`: its `timeline` and `account` views match people by email or LinkedIn profile, which `redact` masks, so they answer with the masked `summary` view and a note naming `--no-redact`. `summary` looks up a lead ref by the tokens `redact` wrote, and `list_hygiene` matches on them. Three things change the list on a real setup:

- A real adapter also serves `vendor_read`, because it has [native reads](/docs/native), but only with `--no-redact`: a native read returns the vendor's payload unmasked, so `redact` turns native reads off.
- `outbound mcp` serves `compare_clients` only with the `clients` plugin from a config file. The CLI always installs the `identity` plugin `person` needs.
- A view or check whose adapter lacks a capability it needs is left out of that tool. On HeyReach that removes `step_funnel` and `campaign_setup`. With `--provider all` one a member can serve stays: one that takes a `campaign` answers for that member's campaigns and refuses the others' before any request, and one that reads every campaign, such as `settings_audit`, answers for the one member that serves it, with `meta.complete: false` and a note naming the members it skipped.

A call to a tool that is left out is answered with a protocol error (`-32602`) whose message names the reason, and a name no tool has is "Unknown tool". A tool one member of `--provider all` serves only on its own, such as `vendor_read`, is named once in `initialize` with the `--provider` that offers it. `--tools` refuses a left-out tool with the same reason before the server starts. `outbound tools` lists what `tools/list` lists, `outbound tool` runs a listed name or an old one, and `outbound insight` lists the insights by their own names, each left-out tool's reason in `meta.notes`.

The `instructions` string repeats the rule about reply text once for the whole server. It is a label for the model, not a safeguard. See [untrusted content](/docs/tools/untrusted-content).

## Build your own server

`createMcpServer(outbound, options)` returns two functions and owns no transport. `serveStdio(server)`, also from `outbound-sdk/cli`, answers standard input on standard output until the input ends, which is all `outbound mcp` does with it. Pass `{ input, write }` to feed it other lines.

| Function | Takes | Returns |
| --- | --- | --- |
| `handle(message, notify?)` | One parsed JSON-RPC message, and where to send progress notifications | The response object, or `undefined` for a notification or a cancelled call |
| `handleLine(line, notify?)` | One line of text, and where to send progress notifications | The response as a JSON string, or `undefined` for a notification, a cancelled call or a blank line |

Options are `only` and `extra` from [`createTools`](/docs/tools#options), plus `version`, which is reported as `serverInfo.version` and defaults to `0.0.0`, and `timeBudgetMs`, the time budget of each tool call in milliseconds (50,000 by default, `Infinity` for none). The budget reaches the reads of tools the server builds itself. For tools you build and pass in `extra`, such as `insightTools(outbound)`, build them on `scope.over(outbound)` from `toolCallScope()` and pass the same `outbound` and `scope` to `createMcpServer`, as `outbound mcp` does. A tool whose reads skip the scope keeps reading past the budget: 5 seconds after it runs out, the call is answered with `RateLimited` and the budget's message, and the next call starts. `outbound mcp` passes the installed package's version. Use it when you want the instance built in your own code, a subset of the tools, or a transport other than stdio. A server you build has only the plugins you give it: `redact()` is the CLI's default, not `createMcpServer`'s.
