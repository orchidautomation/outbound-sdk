Every block on this page is the output of the CLI's own code, run on the in-memory adapter's demo data by the test suite. [The overview](/docs/cli#how-the-samples-run-the-cli) shows the helper that runs it. A line starting with `$` is the command. A line `(exit code 1)` is added by the helper, and a line in square brackets stands in for output too long to print.

The output shows what the CLI does with the demo data. It does not show what a vendor returns. See [what is verified](/docs/status).

## All commands

| Command | Reads | SDK call |
| --- | --- | --- |
| `providers` | The adapters the CLI can load. Needs no adapter. | the provider catalog |
| `capabilities` | What the chosen adapter can do, its maturity and caveats | `outbound.capabilities`, `maturity`, `caveats` |
| `campaigns` | Campaigns | `outbound.campaigns.listAll` |
| `campaign <id or name>` | One campaign, or with a flag its stats, sequence, subsequences or settings | `outbound.campaign(id)` |
| `senders` | Mailboxes and LinkedIn seats | `outbound.senders.listAll` |
| `health <sender id>` | One sender's DNS, sign-in and warmup state | `outbound.sender(id).health` |
| `leads` | Leads, across the account or in one campaign or list | `outbound.leads.listAll` |
| `lists` | Saved lead lists | `outbound.lists.listAll` |
| `replies` | Replies from prospects, one record per message | `outbound.replies.listAll` |
| `thread <id>` | The messages in one conversation | `outbound.thread(id).messages` |
| `stats` | Workspace totals, or one row per day; with `--scope`, a row per campaign or per sender | `outbound.stats` |
| `tags` | Tags | `outbound.tags.listAll` |
| `blocklist` | Blocked addresses and domains | `outbound.blocklist.listAll` |
| `webhooks` | Webhook subscriptions registered at the vendor | `outbound.webhooks.listAll` |
| `limits` | The current rate budget | `outbound.limits` |
| `tools` | The [AI tools](/docs/tools) the instance can serve, then the [insights](/docs/insights), as `outbound mcp` lists them, each with its `name`, `description` and inputs as JSON Schema (`parameters`) | `createTools` with `insightTools` |
| `tool <name>` | Runs one of them. Without `--input`, a tool that has a required input fails with `InputRequired` and exit code 2, with its `name`, `description` and `parameters` in `data` | `tool.call` |
| `insight [name]` | Lists the [insights](/docs/insights), or runs one | `listInsights`, `runInsightByName` |
| `person <email, URL or lead ref>` | Every campaign one person is in, across every tool | `runInsightByName("person_summary")` |
| `native [name]` | Lists the vendor's [own reads](/docs/native), or runs one | `outbound.native` |
| `mcp` | Starts the [MCP server](/docs/cli/mcp) on stdio | `createMcpServer` |
| `help` | The usage text. Also `--help`, `-h`, or no command. |  |
| `version` | The installed version. Also `--version` or `-v`. Needs no adapter. | the package's `package.json` |
| `update` | Whether npm has a newer version, and how to get it. Needs no adapter. | `npm view outbound-sdk version` |

## Flags

| Flag | Commands | Meaning |
| --- | --- | --- |
| `--provider <id>` | all that need an adapter | The adapter to use, or `all` for every provider whose key is set. Overrides `OUTBOUND_SDK_PROVIDER`. |
| `--compact` | all that print JSON | Print the JSON on one line. |
| `--raw` | all that print JSON | Keep each record's `raw`, the vendor's own payload. Left out by default: for a reply it can hold the whole quoted thread, `--bodies` or not. |
| `--help`, `-h` | all | Print the usage text and exit 0. After a command, `outbound leads --help`, print that command's options and the ones every command takes. |
| `--limit <n>` | `campaigns`, `senders`, `leads`, `lists`, `replies`, `tags`, `blocklist`, `webhooks`, `person` | Stop after this many records. A positive whole number. Defaults to 50, except for `leads` and `replies` with `--since`, where it defaults to the whole window, up to 2,000 records. When a listing stops there and more records exist, the command exits **3**, `meta.complete` is `false`, `meta.cursor` says where to resume and `meta.notes` says so, for example "Stopped at 50 leads; more exist. Pass --limit to read more." and "To resume, pass --cursor …", and standard error gets the same sentences. See [the envelope](/docs/cli#the-envelope). |
| `--cursor <cursor>` | `campaigns`, `senders`, `leads`, `lists`, `replies`, `tags`, `blocklist`, `webhooks` | Resume a listing from the `meta.cursor` an earlier run printed, with the same filters. Pages are read at `--limit`'s size, so a run `--limit` stopped ends on a page and the next one repeats no record. Where a page is cut, `meta.repeats` says how many of the first records the next run reads again, so dedupe on `ref`. `meta.cursor` is `null` when the next run starts from the beginning. |
| `--jsonl` | `campaigns`, `senders`, `leads`, `lists`, `replies`, `tags`, `blocklist`, `webhooks`, `thread`, `stats` | Print one record per line as each page arrives, instead of one JSON document, so a load of any size never sits in memory. The last line is the envelope without its data, `{ "meta": ..., "ok": true }`, with `meta.records` counting the lines before it. A failure part way prints `{ "ok": false, "error": ..., "meta": ... }` as the last line, with `meta.cursor` where to resume. For `stats`, each line is a row. `replies --by person` needs every reply first, so its rows are printed at the end. |
| `--status <status>` | `campaigns` | Only campaigns with this status: `active`, `paused`, `draft`, `completed`, `archived` or `unknown`. |
| `--search <text>` | `campaigns` | Only campaigns whose name contains this text, ignoring case. Every campaign is read to find them. |
| `--stats` | `campaign` | The campaign's counts. |
| `--sequence` | `campaign` | The campaign's steps and variants. |
| `--subsequences` | `campaign` | The campaign's subsequences. |
| `--settings` | `campaign` | How the campaign is set up to send. |
| `--from <day>`, `--to <day>` | `campaign --stats`, `stats` | First and last day, `YYYY-MM-DD`. |
| `--scope <scope>` | `stats` | `workspace`, the default, for the account's totals; `campaign` for a row per campaign; `sender` for a row per sender. Every sender is read in batches where the vendor allows it (`stats.bySenders`, Instantly: 200 mailboxes a request); elsewhere `--scope sender` is refused as `Unsupported` before any request, and `--sender` reads one. |
| `--sender <id>` | `stats` | One sender's rows. |
| `--by <grouping>` | `campaign --stats`, `stats`, `replies` | For stats, `day` gives one row per day and `total`, the default, one total row. For `replies`, `person` gives one row per person instead of one per message. Any other value is refused as `Invalid`. |
| `--campaign <id or name>` | `leads`, `replies`, `webhooks` | Only records for this campaign. |
| `--list <id or name>` | `leads` | Only leads in this saved list. |
| `--category <category>` | `replies` | Only replies in this category: `positive`, `negative`, `neutral`, `ooo`, `bounce`, `unsubscribe` or `unknown`. |
| `--since <ISO date>` | `leads`, `replies` | Only leads created, or replies received, on or after this time. A lead created earlier and changed since is not listed. Without `--limit`, every record in the window is read, up to 2,000; a window that holds more stops there with exit code 3, `meta.complete` `false` and a note that names the ceiling. Where the vendor cannot filter by date (`leads.since` or `replies.since` is `client`, such as Instantly's leads), every record is read and the newer ones kept, and a note on stderr and in `meta.notes` says it costs as many requests as reading them all. |
| `--bodies` | `replies`, `thread` | Include message text. Left out by default. |
| `--include-inbox` | `replies` | Also list replies in conversations that belong to no campaign, such as a LinkedIn account's own messages on HeyReach. Left out by default. |
| `--input <json>` | `tool`, `insight`, `native` | The input, as a JSON object in one argument. Defaults to `{}`. |
| `--card` | `tool`, `insight`, `person` | Print the answer as a [card](/docs/cards) in plain text, for a person to read. Not JSON and not in the envelope. |
| `--slack-text` | `tool`, `insight`, `person` | Print the card as text in Slack's mrkdwn, ready to paste into the message composer. Not in the envelope. |
| `--slack` | `tool`, `insight`, `person` | Print the card as a Slack message's JSON alone, `{ text, blocks }`, not in the envelope, ready for `chat.postMessage` or an incoming webhook. Pass one of `--card`, `--slack-text` and `--slack`. |
| `--redact`, `--no-redact` | all that need an adapter | Mask personal fields, or do not. Masking is on by default for `mcp` only. |
| `--cache <seconds>` | all that need an adapter | Reuse an answer for this long, within this process. Each command is a new process, so only `mcp` reuses answers; a one-shot command says so on stderr. Use a store in a config file to persist. |
| `--max-requests <n>` | all that need an adapter | The most vendor requests one command, or one MCP tool call, may make. |
| `--config <file>` | all that need an adapter | Load plugins from a file. |
| `--time-budget <seconds>` | `mcp` | How long one tool call may take before it answers with what it read. Defaults to 50. See [`outbound mcp`](/docs/cli/mcp#a-time-budget-per-tool-call). |
| `--tools <names>` | `mcp` | Offer only these tools, separated by commas. See [`outbound mcp`](/docs/cli/mcp#plugins). |

The last five add [plugins](/docs/cli#plugins); the overview says which plugin each adds and in what order.

A flag a command does not take is refused before any request, with exit code 1: `outbound leads --sender x` writes "Invalid: --sender is not an option of leads". The flags in the last five rows, `--provider`, `--compact`, `--raw` and `--help` are taken by every command.

When `campaign` gets one of `--stats`, `--sequence`, `--subsequences` and `--settings`, its `data` is that answer. Given two or more, `data` holds each answer under its name: `outbound campaign <id> --stats --sequence` prints `data: { "sequence": ..., "stats": ... }`.

A campaign id can be the vendor's id or a `ref` from any record. Other text, such as `"Founders Q4"`, is looked up: the campaigns are read, and a campaign with that id is used as given; failing that, the one whose name matches it whole, ignoring case, or else the only one whose name contains it. When several names match, the command refuses with `Invalid` and lists them. When nothing matches, text that cannot be that vendor's id, such as a name on Instantly, whose ids are UUIDs, is refused with `NotFound` before the vendor is asked. The same holds for `--campaign`, for `leads --list`, and for the `campaign` input of every tool and insight. A count the vendor does not report prints as `null`. The demo campaign has no subsequences, so that command prints an empty array.

## replies and thread

Each record `replies` prints is one message, not one person: a lead who writes twice is two records. `meta.notes` and standard error say how many people and threads sent them, for example "40 messages from 21 people in 9 threads." A count is left out when a reply has no lead or no thread. `--by person` prints one row per `leadRef` instead, with its `messages`, `firstAt`, `lastAt`, `categories` and `threadIds`; replies with no lead are grouped by thread, with `leadRef` `null`.

`thread` lists the conversation's messages in `data.items`, oldest first; an id with no messages exits 1 with `NotFound`. Message text is left out unless you pass `--bodies`: `bodyText` is `null` without it. The CLI prints the text as the vendor returned it. It does not truncate it or mark it as [untrusted content](/docs/tools/untrusted-content), so take care before piping it to a model.

## Loading a warehouse

The CLI can feed a loader. `--jsonl` prints a record per line as each page arrives, so DuckDB's `read_json` or any NDJSON reader takes the output as it is, and the last line, `{ "meta": ..., "ok": true }`, says whether the load is whole. A run `--limit` stopped exits 3, and its `meta.cursor` resumes it. `leads --since` keeps the leads created since a time; a lead created earlier and changed since is not among them, so reload in full now and then to pick up status changes. `stats --scope sender` reads every sender's rows, in batches where the vendor allows it. For loads on a schedule, the [sync plugin](/docs/plugins/sync) keeps the cursor and the time for you.

## tools, tool and insight

`tools` lists the [AI tools](/docs/tools) and the insights, as `outbound mcp` serves them, each with its inputs as JSON Schema in `parameters`, and `tool` runs any of them with the same input a model would send. Given no `--input`, a tool with a required input prints its `name`, `description` and `parameters` instead of failing. `insight` with no name lists the 27 insights with their input schemas, and with a name runs one.

Both commands exit 1 on failure, with `ok: false` and the `error` in the envelope, except `outbound tool` given no input it needs, which exits 2. A tool never throws, so `outbound tool` prints its result there with `next`, and writes nothing to standard error. An insight throws, so `outbound insight` also writes `<code>: <message>` to standard error.

`tools` lists `cross_channel_lead` because the CLI always installs the [identity](/docs/plugins/identity) plugin, and leaves it out with `--redact`, which masks the identifiers it matches on. It lists `compare_clients` only with the [clients](/docs/plugins/clients) plugin, from a file passed to [`--config`](/docs/cli#plugins). The insights are listed after the built-in tools, as `outbound mcp` serves them.

## person

`person` takes an email address, a LinkedIn profile URL or a lead ref exactly as another command printed it (a reply's `leadRef`, a lead's `ref`), and prints the `person_summary` insight: every campaign that person is in, in every tool the CLI reads. With several vendor keys set and no provider named, that is every one of them, so one command finds a person on Instantly and on HeyReach. `--card` and `--slack` print it as a [card](/docs/cards), as `tool` and `insight` do.

A `mailto:` link is read as the address in it. A company domain such as `acme.com` or `@acme.com` is refused with `Invalid` and a pointer to `account_summary`, and text with an `@` that is not an email address is refused too, both before any request. A person who is in no campaign is an answer, `found: false`, with exit code 0. With `--redact` the emails and profiles it would match are masked, so the command refuses with `Unsupported` rather than report a known person as not found.

## version and update

`outbound version` prints the installed version and nothing else, so a script can read it. `outbound --version` and `outbound -v` do the same.

`outbound update` asks npm for the newest published version, through the `npm` on your `PATH`. If you already have it, the command says so and changes nothing. Otherwise what it does depends on how the package was installed:

- **Global install** (`npm install --global outbound-sdk`): it runs `npm install --global outbound-sdk@<version>` with the version npm just named. For a few minutes after a release, npm lists the new version before it serves the download, and the install fails with `E404` or `ETARGET`. `update` then tries again every 30 seconds for up to 15 minutes, and says so once.
- **Installed in a project**: it prints `npm install outbound-sdk@latest` for you to run. It does not run it, because that would rewrite the project's `package.json` and lockfile.
- **Run through npx**: it prints `npx outbound-sdk@latest <command>`, since npx keeps its own copy.

If npm cannot be reached, or the install fails for another reason, such as `EACCES` on a global folder you cannot write to, the command exits with code 1 and prints npm's error code and the line that says what went wrong.

## mcp

`outbound mcp` does not print a result and exit. It reads JSON-RPC messages from standard input until it closes. See [`outbound mcp`](/docs/cli/mcp).
