The package ships one binary, installed under two names: `outbound` and `outbound-sdk`. It is a thin shell over the SDK: each command makes the same read you would make in code and prints the result as JSON. It adds no behaviour of its own, and like the SDK it only reads.

Run it with `npx outbound-sdk <command>`. That works with or without the package installed: npx uses the project's copy when there is one and downloads the package otherwise. Inside a project that has the package, `outbound <command>` from a package script, or `node_modules/.bin/outbound`, runs the same binary. After `npm install -g outbound-sdk`, `outbound <command>` works from any folder (see [installation](/docs/installation#the-cli-on-your-path)). Do not type `npx outbound` outside such a project: `outbound` on npm is an unrelated package, and npx would download it.

## How the samples run the CLI

Every command shown in this section went through `run`, the function the `outbound` executable calls, exported from `outbound-sdk/cli`. The helper below runs it in the test process with the provider set to `memory`, prints a `$ outbound ...` line, then what the CLI wrote. The executable itself, as a separate process, is covered by the SDK's own tests and is not what these samples start.

<include meta='title="cli.ts"'>../../_examples/cli-commands/cli.ts</include>

`run(argv, io)` takes the arguments after `outbound` and an object with `stdout` and `stderr` functions, and resolves to the exit code. You can call it the same way to embed the CLI in a script. `io.stdin` supplies lines for `outbound mcp`, and `io.adapter` replaces the adapter the environment would choose, which is meant for tests.

## Choosing the provider

A command that reads data needs an adapter. The CLI builds one from the environment:

1. `--provider <id>` if given, otherwise the `OUTBOUND_SDK_PROVIDER` environment variable.
2. An id is one of `instantly`, `smartlead`, `heyreach` or `memory`, or `all`.
3. `all` builds every provider whose key is set (`INSTANTLY_API_KEY`, `SMARTLEAD_API_KEY`, `HEYREACH_API_KEY`), with no list to maintain: one key gives that provider alone, several give one [combined](/docs/adapters/combine) instance, where every record keeps its own provider, so `outbound person` looks a person up in all of them. Set another key and its tool is included the next time the command starts. `memory` is never part of `all`.
4. With neither `--provider` nor `OUTBOUND_SDK_PROVIDER` set, the CLI does the same as `all`. With no key set either, the command exits with code 1 and names the variables.
5. Each adapter reads its own key from the environment. `outbound providers` lists the variables each one reads.

`memory` needs no key. It runs on a small built-in demo data set, the same one behind `demoData()` in `outbound-sdk/memory`: two campaigns, three leads, a few messages. Use it to try a command before pointing the CLI at a real account.

```sh
# a real account
export INSTANTLY_API_KEY=...
outbound campaigns --status active

# two tools: both are read, and one person is found in each
export HEYREACH_API_KEY=...
outbound person someone@example.com

# the demo data, for one command
outbound campaigns --provider memory
```

Those shell lines are not run by the test suite. The CLI takes no key on the command line.

## Plugins

A command runs with one [plugin](/docs/plugins) by default, [identity](/docs/plugins/identity), which links one person's records across tools for `outbound person`. `outbound mcp` is the exception: it runs with [`redact()`](/docs/plugins/redact) unless given `--no-redact`, because what it returns goes to a model. Any command takes these options:

| Option | Adds |
| --- | --- |
| `--redact` | `redact()`: masks personal fields. On by default for `outbound mcp` only. |
| `--no-redact` | Turns the default `redact()` off for `outbound mcp`. |
| `--cache <seconds>` | `cache()` with that time to live. The cache is in memory and lasts one process, so it helps `outbound mcp`; a one-shot command says so on stderr. To keep answers across runs, list `cache({ ttl, store })` with your own store in a config file. |
| `--max-requests <n>` | `budget({ maxRequests: n, per: "run" })`. A command is one run; on the MCP server each tool call is one. It also replaces an insight's default cap, and cap messages name the flag. |
| `--config <file>` | The plugins a file lists as `export default defineConfig({ plugins: [...] })`. |

[The MCP server page](/docs/cli/mcp#plugins) has a run of each, the order the plugins are placed in, and what a config file may hold. How far each real adapter has been checked is on [what is verified](/docs/status).

`help` and `providers` need no adapter and work with nothing set.

## Output

A command prints one JSON value on standard output, always in the same shape, the envelope: indented by default, on one line with `--compact`. Records in it are the SDK's [records](/docs/api/records), less `raw`, the vendor's own payload; `--raw` keeps it. List commands stop at `--limit`, which defaults to 50.

## The envelope

Every command prints the same top-level keys, so a script or an agent parses one shape and learns from standard output whether the answer is whole: `{ ok, data, meta: { complete, notes, provider, requests }, next }`.

| Key | Holds |
| --- | --- |
| `ok` | `true` when the command got its answer, `false` when it failed. |
| `data` | The answer. A list is in `data.items`. A record is the record without its `meta`. An insight's answer, a vendor read from `native` and a tool's result are their `data`. `null` on failure. |
| `error` | On failure only: `code` and `message`, the same as standard error's `<code>: <message>`. |
| `meta.complete` | `true` when the answer covers everything asked, `false` when it covers part of it, for example when `--limit` cut a list or a cap stopped a read. |
| `meta.notes` | Why `complete` is `false`, and what else to know, for example "Stopped at 50 leads; more exist. Pass --limit to read more." Standard error gets the same notes. |
| `meta.provider` | The adapter's id, or `null` for `providers`, which needs none. |
| `meta.requests` | The vendor requests the command sent. A cache hit sends none. |
| `next` | What to ask next, from a tool. Left out by other commands. |

The rest of a record's, a tool's or an insight's `meta`, such as `evidence` and `fetchedAt`, stays in `meta` beside these; an insight's name is `meta.insight`. `--card` and `--slack` put the card or the Slack message in `data`. The MCP server, `version` and `update` do not print JSON, so they print no envelope.

## Exit codes and errors

| Exit code | When |
| --- | --- |
| `0` | The command ran and got its answer. |
| `1` | Anything else: an unknown command or option, a missing argument, a flag value that is not one of the allowed words, a record that does not exist (a campaign, sender, thread, or the campaign or list `leads` reads), a read the adapter cannot serve, a rejected key, or a tool whose result is `{ "ok": false }`. |

A failure prints its envelope on standard output, `{ "ok": false, "data": null, "error": { "code", "message" }, "meta" }`, and `<code>: <message>` on standard error, where the code is an [`OutboundError` code](/docs/api/errors) such as `Invalid`, `NotFound`, `Unsupported` or `Unauthorized`, or `Error` for a failure that is not an `OutboundError`. A tool whose result is `{ "ok": false }` prints it in the envelope, with the tool's `error` and `next`, and writes nothing to standard error.
