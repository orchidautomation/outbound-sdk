The vendors do not offer the same reads. One cannot read a campaign's settings, another cannot list the leads of a saved list. Each adapter declares what it can do as a flat map of keys, and `outbound.capabilities` is that map. Reading it sends nothing.

Two rules follow from the map:

- **A read the adapter cannot serve is refused before any request.** It throws `Unsupported`, naming the key. You never get an empty list that means "not supported".
- **Anything an adapter does not declare is `false`.** An adapter that says nothing never advertises a wrong yes.

## Every key

`CAPABILITY_KEYS` is the list of all 53. `Capabilities` is the type of the map, and `CapabilityKey` the type of a key.

### Campaigns and sequences

| Key | Values | Gates |
| --- | --- | --- |
| `campaigns.status` | `server`, `client`, `false` | The `status` filter on `campaigns.list` |
| `campaigns.bySender` | boolean | `campaigns.list({ senderId })` and `sender(id).campaigns` |
| `campaigns.progress` | boolean | `campaign(id).progress()` |
| `campaigns.settings` | boolean | `campaign(id).settings()` |
| `sequence` | boolean | `campaign(id).sequence()` |
| `sequence.subsequences` | boolean | `campaign(id).subsequences` |

Listing campaigns and reading one need no key. Every adapter can.

### Senders

| Key | Values | Gates |
| --- | --- | --- |
| `senders.list` | boolean | `senders.list` with no `campaignId` |
| `senders.byCampaign` | boolean | `senders.list({ campaignId })` and `campaign(id).senders`. Does not need `senders.list`. |
| `senders.get` | boolean | `senders.get`, `sender(id).get()`, and `sender(id).warmup()` |
| `senders.warmup` | boolean | `sender(id).warmup()` |
| `senders.health` | boolean | `sender(id).health()` |
| `senders.healthList` | boolean | `senderHealth.list` and `senderHealth.listAll`: every sender's health a page at a time, with `campaignId` too where `senders.byCampaign` is true |

### Leads and lists

| Key | Values | Gates |
| --- | --- | --- |
| `leads.list` | boolean | `leads.list` across every campaign, with no `campaignId`, `listId` or lookup |
| `leads.byCampaign` | boolean | `leads.list({ campaignId })` and `campaign(id).leads`. Does not need `leads.list`. |
| `leads.get` | boolean | `leads.get` and `lead(id).get()` |
| `leads.lookup` | boolean | The `email` and `linkedinUrl` filters: finding a lead without walking every lead |
| `leads.byDomain` | boolean | The `domain` filter: the leads whose email address is at exactly one domain, without walking every lead |
| `leads.lookupMany` | boolean | The `emails` filter: the leads of many exact email addresses in one listing, without one lookup each |
| `leads.byInterest` | boolean | The `interest: "positive"` filter: only the leads the vendor labels positive, without walking every lead |
| `leads.byStatus` | boolean | The `status: "active"` filter: only the leads still in the sequence, without walking every lead. Not together with `interest` |
| `leads.since` | `server`, `client`, `false` | The `since` and `until` filters on leads |
| `leads.timeline` | boolean | `lead(id).timeline()` |
| `leads.engagement` | boolean | No read on the instance. It says whether leads carry `engagement`: open, click and reply counts. Some [insights](/docs/insights) check it. |
| `lists.list` | boolean | `lists.list` |
| `lists.get` | boolean | `lists.get(id)` and `list(id).get()` |
| `lists.leads` | boolean | `leads.list({ listId })` and `list(id).leads` |

### Messages and replies

| Key | Values | Gates |
| --- | --- | --- |
| `messages.list` | boolean | `messages.list`, `campaign(id).messages`, `lead(id).timeline()`, `thread(id).messages()` |
| `messages.byThread` | boolean | The `threadId` filter and `thread(id).messages()` |
| `messages.byHand` | boolean | The `byHand` filter on messages: only the ones a person sent by hand, not by a campaign |
| `messages.since` | `server`, `client`, `false` | The `since` and `until` filters on messages |
| `messages.body` | `full`, `sampled`, `false` | `include: ["body"]` on messages and on replies |
| `replies.list` | boolean | `replies.list` and `campaign(id).replies` |
| `replies.category` | `vendor`, `false` | The `category` filter on replies |
| `replies.since` | `server`, `client`, `false` | The `since` and `until` filters on replies |
| `replies.unread` | `server`, `client`, `false` | The `unread` filter on replies |
| `replies.inbox` | boolean | Nothing is refused. `true` when the vendor's inbox also holds conversations in no campaign: their replies are left out of `replies.list` unless you pass `includeInbox: true`, and their messages carry a `null` `campaignRef` |

`messages.body` is `full` when the vendor returns every body and `sampled` when it returns some. `replies.category` is `vendor` when the categories come from the vendor. The SDK never asks a model to classify a reply.

### Stats

| Key | Values | Gates |
| --- | --- | --- |
| `stats.workspace` | `exact`, `derived`, `false` | `outbound.stats()` |
| `stats.campaign` | `exact`, `derived`, `false` | `campaign(id).stats()` |
| `stats.allCampaigns` | `full`, `partial`, `false` | `stats({ scope: "campaign" })` with no `scopeId`: a row per campaign in one call. `full` when each row has every count the read of one campaign has, `partial` when the vendor's report has fewer. |
| `stats.byStep` | `exact`, `derived`, `false` | `campaign(id).stats({ scope: "step" })` |
| `stats.bySender` | `exact`, `derived`, `false` | `sender(id).stats()` |
| `stats.bySenders` | `exact`, `derived`, `false` | `stats({ scope: "sender", scopeIds })`: several senders' rows in one call, a few requests in all instead of a few per sender. Needs `stats.bySender` as well. |
| `stats.byDay` | `exact`, `derived`, `false` | `by: "day"` on any of the four, in addition to the scope's own key |

| `blocklist` | boolean | `blocklist.list` |
| `placementTests.list` | boolean | `placementTests.list()`: the inbox placement tests the account has set up |

### Webhooks and sync

These describe the adapter. No call on the instance is gated on them.

| Key | Values | Says |
| --- | --- | --- |
| `events.parse` | boolean | The vendor's webhook payloads can be parsed into events. See [webhooks](/docs/webhooks). |
| `events.verify` | `signature`, `secret`, `false` | How a webhook is authenticated: a signature the vendor computes, or a shared secret you put in the URL or a header. See [verification](/docs/webhooks/verification). |
| `deletionDetection` | boolean | Whether list calls reveal deleted records. |

## Filter grades

A filter key is `server`, `client` or `false`.

| Grade | What happens | Result is marked |
| --- | --- | --- |
| `server` | The vendor filters. | `exact` |
| `client` | The vendor cannot. The SDK fetches each page unfiltered and filters it before handing it to you. | `derived` |
| `false` | The filter is refused with `Unsupported`. |  |

<include lang="text" meta='title="Output"'>

A `client` filter gives the right records and costs more to get them:

- **Every page is fetched.** Asking for the last day of leads still walks every lead. The cost is that of the unfiltered listing.
- **Pages come back short.** A page can hold fewer records than `limit`, or none, with more pages to come. Go by `cursor`, not by how many items arrived. See [pagination](/docs/api/pagination#limit).
- **`meta.evidence` is `derived`** on that result, so code downstream can tell. See [results](/docs/api/results#evidence).

Without the filter the same listing is `exact`. The grade only applies when the filter is used.

## Stat grades

A stat key is `exact`, `derived` or `false`: the vendor reports the numbers, the adapter computes them from other vendor data, or they are not available. A stats result is `derived` when any of its rows is. See [stats](/docs/api/stats#grades).

## Field grades

A capability says whether a read exists. `outbound.fields` says what the read can tell you: for every field of every record, whether this adapter fills it.

| Grade | Means |
| --- | --- |
| `exact` | The vendor reports the field and the adapter reads it. A `null` means this record has no value. |
| `derived` | The adapter computes the field, or takes it from a neighbouring record. A reply's category on Smartlead and HeyReach is the lead's label, not a label on the message. |
| `false` | The adapter never fills the field. It is always `null`, `[]`, `{}` or `unknown`, because the vendor has no such field. |

A vendor with no field for a job title or a LinkedIn profile often still holds one in a custom field the account named itself. The SDK guesses only a LinkedIn profile: without a `linkedinUrl` mapping, a custom field named `linkedin`, `linkedin url`, `linkedin profile` or `linkedin profile url` (case, spaces, underscores and hyphens ignored) is read when its value is a linkedin.com/in/ URL, so Instantly's `linkedinUrl` is `derived`. For anything else, pass `leadFields` to the adapter, naming the custom field for `title`, `company`, `phone`, `website`, `location`, `linkedinUrl` or `companyLinkedinUrl`, and the adapter reads it wherever the vendor's own field is empty. A field that was `false` then reports `derived`.

A record the adapter never returns has every field `false`. On a [combined](/docs/adapters/combine) instance a field is filled when any adapter behind it fills it. The repository's test suite holds each adapter to its declaration both ways: a field declared `false` is empty in every record its fixtures produce, and every other field is filled in at least one.

## Change what an adapter declares

Each vendor adapter takes a `capabilities` option that overrides what it declares. Use it when your account differs from the default: a plan without an endpoint, or a key that cannot read one.

</include>

<include lang="text" meta='title="Output"'>
  ../_examples/capabilities/override.out.txt
</include>

A key you turn off is refused up front like any other. On Instantly, turning `tags` off also stops the two extra requests a campaign listing makes to read tag names, and campaigns then come back with empty `tags`.

A declaration is a claim. Turning a key on does not give a vendor an endpoint it lacks: the call then fails, as `Unsupported` when the adapter has no read for it, or with whatever the vendor answers.

The [in-memory adapter](/docs/adapters/memory) takes the same option. That is how the samples on this site run code "as" a vendor: see [how the samples are run](/docs/samples).

## Plugins can only narrow

A plugin may change the map the instance advertises, and only downwards. A plugin that turns something off is named in the refusal. A plugin that tries to turn something on is ignored.

`outbound.capabilities` is the map after every plugin. The [redact](/docs/plugins/redact) plugin uses this: it turns off `native`, and `messages.body` when bodies are being masked, so a read that would return unmasked text is refused and not quietly passed through.

A [combined](/docs/adapters/combine) instance works the same way. Its map holds, for each key, the weakest value among its adapters, so it promises only what every one of them can do. `outbound.workspace(id).capabilities` is the map for one of them.

## Helpers

Exported from `outbound-sdk` for code that works with the maps directly, such as an adapter or a plugin:

| Export | Does |
| --- | --- |
| `CAPABILITY_KEYS` | Every key, as an array. |
| `NO_CAPABILITIES` | A map with every key `false`. |
| `resolveCapabilities(declared?)` | A partial declaration filled out with `false`. |
| `intersectCapabilities(first, ...rest)` | For each key, the weakest value across the maps. |

"Weakest" orders the values: `false` is below `client`, `derived`, `sampled` and `secret`, which are below `server`, `exact`, `full`, `signature`, `vendor` and `true`.
