`alerts({ rules, notify })` from `outbound-sdk/alerts` checks every record a read returns against a list of rules and calls your `notify` function with the alerts that fired. A rule is arithmetic on one record the read returned: a rate against a threshold, a status against a value. No model is involved. The plugin fetches nothing, schedules nothing and remembers nothing: rules run only on the reads you make.

The bounce and reply alerts appear three times: once for the two-day total, and once for each day of the by-day read, which is a separate read returning separate rows. By default nothing removes repeats. Pass `dedupe` to be told about each one once (see [what counts as a repeat](#what-counts-as-a-repeat)).

## Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `rules` | `AlertRule[]` | required | Checked against every record, in order. |
| `notify` | `(alerts: Alert[]) => void \| Promise<void>` | required | Called once per operation that fired at least one alert, with all of that operation's alerts. Not awaited. |
| `dedupe` | `AlertDedupe` | none | A store of the alerts already notified: `has(key)` and `add(key)`, sync or async. With it, an alert is notified once, however many reads show it, and `notify` gets only the alerts not seen before. The key is in [what counts as a repeat](#what-counts-as-a-repeat). `memoryAlertDedupe()` keeps the keys in this process's memory, for one run. Supply your own to remember across runs: the SDK stores nothing itself. A store that fails is ignored and cannot fail the read; nothing is notified for that read. |

## Built-in rules

| Rule | Fires for | Alert `rule` |
| --- | --- | --- |
| `bounceRateAbove(threshold, { minSent })` | A stats row whose bounce rate (bounced divided by sent) is above `threshold`, a fraction from 0 to 1. | `bounce-rate-above` |
| `replyRateBelow(threshold, { minSent })` | A stats row whose reply rate is below `threshold`. The rate is replies divided by leads contacted, or by messages sent when the vendor does not report contacted. | `reply-rate-below` |
| `senderNotActive()` | A sender whose status is anything except `active` or `unknown`. | `sender-not-active` |
| `noSends()` | A stats row for one day (`date` is set) whose `sent` is exactly `0`. | `no-sends` |

Both rate rules skip a row with fewer sends than `minSent` (default `50`), and a row whose rate is `null` because the vendor did not report a count. A missing count never fires a rule.

`noSends()` needs the vendor to return a row for the silent day. A vendor that leaves empty days out of its daily stats gives it nothing to check.

## Alerts and your own rules

An `Alert` is:

| Field | Type | Meaning |
| --- | --- | --- |
| `rule` | `string` | The rule's name. |
| `subject` | `string` | The ref of the campaign, sender or workspace it is about. For a stats row, its `scopeRef`. |
| `subjectName` | `string \| null` | The subject as a person knows it: the sender's address, or the campaign's name when this instance has already read that campaign record. `null` when neither is known; `alertCard` then shows the ref. |
| `message` | `string` | A sentence, for example "Bounce rate is 9%, above 5%". |
| `value` | `number \| string \| null` | What was measured. |
| `threshold` | `number \| string \| null` | What it was compared with. |
| `day` | `string \| null` | The day of the stats row, `YYYY-MM-DD`, for an alert about one day's counts. `null` for a row that totals a range. Absent from an alert about another record. |

An `AlertRule` is `{ name, check, state? }`, where `check(record)` returns an `Alert` or `null`. It receives every kind of record the instance returns, so it starts by telling them apart, as `untaggedCampaign` does in the sample. A rule sees one record at a time. Anything that needs two records, or a change since last week, is not a rule: see [insights](/docs/insights). Set `state: true` on a rule about a state, such as a status, so that `dedupe` tells you when the value changes.

## What counts as a repeat

With `dedupe`, an alert is a repeat of one already notified when it has the same key:

| Alert | Key | So |
| --- | --- | --- |
| About one day's stats row (`day` is set) | `rule\|subject\|day`, for example `no-sends\|instantly:ws:c1\|2026-11-10` | No sends on 11-10 and again on 11-11 is two alerts. A second run over 11-10 is not a new one. |
| From a state rule (`state: true`, as `senderNotActive()` is) | `rule\|subject\|value`, for example `sender-not-active\|instantly:ws:s1\|paused` | A sender paused, then in error, is two alerts. One that stays paused is one, and so is one that goes back to a status already notified. |
| Anything else: a row that totals a range, or your own rule without `day` or `state` | `rule\|subject` | Notified once for that subject, whatever its value. |

Each key is stored in your `dedupe` store as it is notified. A rate that changes on a day already notified is not a new alert.

## What it adds

| Member | Returns |
| --- | --- |
| `outbound.alerts.evaluate(records)` | The alerts those records fire. It does not call `notify`. |

Use `evaluate` to check records you already hold, or to test a rule.

## What it changes

It changes no capability, no record and nothing in `meta`. Records pass through untouched.

## With other plugins

- Inside `cache`, rules run once per real read. Before `cache`, they run on every read, cache hits included.
- Listed after `redact`, rules see unmasked records. An alert `message` you build from a lead's fields carries them unmasked to your notifier.
- A stats row served stale by `failover` fires the same alerts as a fresh one. The rule cannot see `meta`.

| What happened | What you get | What to do |
| --- | --- | --- |
| `notify` throws or rejects | Nothing. The read succeeds and the alerts are lost. | Make the notifier retry or queue on its own. |
| `notify` is slow | Nothing. The read does not wait for it. | An alert can arrive after the read returns. |
| A rule's `check` throws | The read fails with that error | Guard a rule you write against records it does not expect. |
| The read fails | No rules run | Nothing. A failed read is not an alert. Watch for errors with [hooks](/docs/api/hooks). |
| A row is too small for a rate | No alert | Lower `minSent` if small rows matter to you. |
