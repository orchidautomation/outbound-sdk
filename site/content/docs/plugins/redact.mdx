`redact()` from `outbound-sdk/redact` masks personal fields in the records an instance returns, before they reach a caller, an agent or a report. It always sets `raw` to `null`, because the vendor's payload holds everything the normalized fields were taken from. It fails closed: a record it does not recognise is refused, never passed through. List it first, so it is the outermost layer.

## Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `fields` | `RedactField[]` | all eight | What to mask: `"email"`, `"name"`, `"phone"`, `"company"`, `"linkedin"`, `"custom"`, `"subject"`, `"body"`. |
| `strategy` | `"mask" \| "hash"` | `"mask"` | `mask` replaces a value with `[redacted]`, and an email address or a LinkedIn profile with a token keyed for this plugin (see [Ids and refs](#ids-and-refs)). `hash` replaces every value with `redacted:` and 16 hex characters derived from the value, so the same value always gives the same token, from one run to the next. Under both, people can still be counted and joined. |
| `key` | `string` | none: a random key per plugin | A secret of at least 32 characters (`MIN_KEY_LENGTH`) that keys the tokens `mask` writes for addresses and profiles, so the same person gets the same token in every instance and process given the same key. See [A fixed key](#a-fixed-key). Only with `mask`. |

A `null` value stays `null` under both strategies. The subpath also exports `ALL_FIELDS`, `MASK` (the string `[redacted]`) and `MIN_KEY_LENGTH` (32).

The token is a hash of the value with no secret mixed in. Anyone who can guess an address can compute its token and confirm the guess. Treat hashed output as pseudonymous, not anonymous.

## What it masks

| Record | Masked, by field | Left as it is |
| --- | --- | --- |
| Lead | `email` (`email`), `firstName` and `lastName` (`name`), `phone` (`phone`), `company`, `website` and `companyLinkedinUrl` (`company`), `linkedinUrl` (`linkedin`), every value in `custom` (`custom`). Custom field names are kept. | `title`, `location`, `status`, `progress`, `replied`, `bounced`, `unsubscribed`, `tags`, `interest`, `interestCategory`, `engagement`, dates |
| Message, reply | `subject` (`subject`), `bodyText` and `bodyHtml` (`body`) | Dates, direction, category |
| Sender | `address` (`email`), `linkedinUrl` (`linkedin`), `name` (`name`) | Status, limits, warmup, `mailProvider`, `tags` |
| Block list entry | `value`, when the entry is an email address or a LinkedIn profile | A blocked domain, and any other kind |
| Stats row | Nothing but its `scopeRef` (see below). It holds counts only. | Everything else |
| Campaign, workspace, sequence, settings, sender health, list, tag, webhook | Nothing but ids and refs (see below) | Everything except `raw` |
| Every record | An email address (`email`) or a LinkedIn profile URL (`linkedin`) inside `ref`, `sourceId` or any field whose name ends in `Ref` or `Refs` | An id the vendor made up, such as a number or a UUID |

Every record except a stats row has `raw` set to `null`, whatever `fields` says. Sequence steps are template text and are not masked.

### Ids and refs

Some vendors use personal data as an id. Instantly addresses a mailbox by its email address, so a sender's `ref` and `sourceId` hold it, and so does every `senderRef` that points at the sender. An Instantly message names its lead by address too, in `leadEmail`. HeyReach identifies a lead by its LinkedIn profile URL, which then sits in the lead's `ref` and in the `leadRef` of its messages.

`redact` masks that part of `ref`, `sourceId` and every `*Ref` field, on records and on webhook events, when the matching field (`email` or `linkedin`) is being masked:

- With `mask`, the address or the URL becomes `redacted:` and 16 hex characters of an HMAC-SHA-256 under a random key the plugin makes and never gives out, or under the `key` you give it. One person gets one token, so two people keep two refs and every count and join by ref holds; the `email`, `address` and `linkedinUrl` fields get the same token, so an Instantly reply's `leadEmail` still names its person. The random key lives as long as the plugin: tokens hold within one instance, one CLI command or one `outbound mcp` session, and differ in the next, so they cannot be looked up from an address. With a `key` they hold wherever that key is used.
- A call that names a token this plugin wrote, in a ref or a field, reaches the vendor with the value in its place, and its answer comes back masked; a vendor error quotes the token, not the value. That is how an insight reads the lead behind a reply. The values live only in this plugin's memory, at most the newest 10,000 of them, and are never written out or returned.
- A call that names a token this plugin did not write, such as one kept from an earlier CLI command or MCP session, is refused as `NotFound` before any request, and the token is never sent to the vendor. The error says the token is from another session or process. Read it again in this session, or give a `key` (`OUTBOUND_REDACT_KEY` for the CLI and MCP server) so tokens stay the same across runs.
- With `hash`, it becomes the same token every time, so a record keeps its `ref` from one run to the next and a `senderRef` still equals the sender's `ref`. An address gives the token its `email` or `address` field gets.

Either way, a masked ref never becomes one shared `[redacted]`, which would merge every lead into one.

A masked ref cannot be passed back to `outbound.sender(ref)` or `outbound.lead(ref)`: it no longer holds the vendor's id.

What stays: an id that is not an address or a profile URL is not personal data and is left as it is. A bare profile slug with no URL around it cannot be told from such an id, and stays too.

### A fixed key

Pass `key` when redacted data has to join across runs: a warehouse loaded every night, notes kept from one `outbound mcp` session to the next, or two machines comparing answers. The token for an address or a profile is then the same in every instance and process that holds the key, and a different key gives different tokens. The CLI and `outbound mcp` read it from `OUTBOUND_REDACT_KEY`.

The key is a secret, and should be handled like a vendor API key:

- **Anyone who holds it can test guesses.** With the key and a list of candidate addresses, they can compute each token and see who is in your data. Without it, a token cannot be traced back to anyone. Keep it in a secret store or an environment variable, never in a repository, a config file you share or a prompt.
- **A new key gives every person a new token.** After you rotate it, records loaded under the old key no longer join with new ones. Re-load what you keep, or keep the old key for the old data.
- **Generate it, do not invent it.** `openssl rand -hex 32` gives 64 random characters. `redact` refuses a key shorter than 32 characters, and a key given with `strategy: "hash"`, with `Invalid` when the plugin is built, before any request.

`redact` keeps the key in memory only. It is never written to a record, an answer, a note, `meta`, a card or an error message. A `redact()` in a CLI config file takes its own options, so pass the key there as `redact({ key: process.env.OUTBOUND_REDACT_KEY })`.

## What it turns off

| Capability | Becomes | When | Why |
| --- | --- | --- | --- |
| `messages.body` | `false` | `fields` includes `"body"` (the default) | Asking for bodies while they are being removed is a contradiction, so the call is refused up front. |
| `native` | `false` | Always | A native read returns the vendor's payload untouched. |

[`outbound.raw`](/docs/api/raw) has no capability of its own, and returns the same untouched payload. It is refused as `Unsupported` on an instance with `redact`, whether or not the adapter has native reads.

It changes nothing in `meta`.

## What it adds

| Member | Holds |
| --- | --- |
| `outbound.redacted` | `{ fields, strategy, hash, resolves, leadsByToken }`: the fields being masked, sorted, `"mask"` or `"hash"`, and `hash(value)`, the text this redact writes in place of `value` in a masked field (the token under `hash`, `[redacted]` under `mask`, whose keyed tokens it never gives out), so a known address can be found among hashed records. `resolves(token)` says whether a token this redact wrote stands for an `email` or a `linkedin` profile, or `null`, without giving the value. `leadsByToken(tokens, campaign)` reads the leads behind address tokens and returns them masked. Other plugins and the tools read it to know what they cannot see. |

## Webhook events

The plugin also has an `event` hook, which runs when you pass the instance's plugins to `parse()` from `outbound-sdk/webhooks` (see [webhooks](/docs/webhooks)). It sets the event's `raw` to `null` and rewrites `data`:

- `leadEmail`, `leadName`, `linkedinUrl`, `subject` and `text` are masked by their field, when they are strings. A value of another type becomes `null`.
- Any other key keeps a plain value (string, number, boolean, `null`).
- Any other key holding an object or an array becomes `[redacted]`, because it could hold anything.

## With other plugins

List `redact` first. It masks what the layers inside it return, so `cache`, `failover` and `fixtures` inside it see, and store, unmasked records. To keep masked data in a store, list that plugin before `redact`.

`redact` masks the fields it knows and passes every other field through:

- `clients` adds `client`, your own label. It passes through.
- `identity` adds `personKey` and `personKeys`, which hold the email address and the profile slug. `redact` masks the part after `email:` or `linkedin:` when that field is being masked: under `mask` the keyed token the lead's `email` gets, or with `hash` `email:redacted:` and 16 hex characters, the same token the lead's `email` gets.
- `outbound.person()` is refused as `Unsupported` while `redact` masks `email` or `linkedin`, because it links records by those identifiers and would see none. The `cross_channel_lead` tool is not offered then. With a `fields` list that leaves both out, `person()` works as usual.
- [`insights`](/docs/insights) and the method-only plugins (`exporter`, `sync`, `reconcile`, `benchmarks`) read through the instance, so they receive masked records. An insight that matches records by a masked field refuses with `Unsupported` before any read, naming `redact`, and is left out of `insightTools`, instead of answering with nobody found:
  - `person_summary`, and so `outbound person`, refuses an identifier of a masked kind under `mask`. Under `hash` it hashes the address or profile URL given the way `redact` does and matches the hashed records. A lead ref is looked up by the lead's email address when that is not masked, or else by its LinkedIn profile; it is refused when neither is left, and under `hash` when the one it would use is hashed (give the address or the profile URL instead). With one of `email` and `linkedin` masked it says the records under the masked one were not linked. It is left out of the tools while both are masked with `mask`.
  - `account_summary` refuses while `email` is masked, with either strategy: no domain is left to match, and a hashed address keeps none.
  - `suppression_check` and `lead_collisions` match by the masked values themselves. Under `mask` the token an address or a profile gets is keyed for this plugin and written from the lowercased address or the profile's slug, so the same person has the same token on every record and every block list entry the plugin returns, and the answer names them by token. They are tokens of this run: another process or another `redact` writes others. With `hash` they match by the hashed address. Both say what they could not match: domain entries, since a masked address keeps no domain, and with `hash` LinkedIn profiles too, since a hashed URL keeps no slug.

| What happened | What you get | What to do |
| --- | --- | --- |
| A read asks for bodies (`include: ["body"]`) | `Unsupported`, before any request. The message names the plugin. | Leave bodies out, or construct `redact` with `fields` that do not include `"body"`. |
| A native read, or any `outbound.raw` request | `Unsupported`, before any request. The message names the plugin. | Use a second instance without `redact` for those reads, and handle its output as unmasked. |
| `outbound.person()` while `email` or `linkedin` is masked, or `person_summary` with an identifier of a kind masked with `mask` | `Unsupported`, before any read | Look the person up on an instance without `redact`, use `strategy: "hash"`, or leave both fields out of `fields`. |
| `person_summary` with a lead ref whose email address and LinkedIn profile are both masked, or hashed | `Unsupported` | Give the person's email address or profile URL, which `hash` can match. |
| `account_summary` while `email` is masked | `Unsupported`, before any read. The message names the plugin. | Run it on an instance without `redact`. |
| A `key` shorter than 32 characters, or a `key` with `strategy: "hash"` | `Invalid`, when the plugin is built. The message never holds the key. | Generate one with `openssl rand -hex 32`, or drop `key` under `hash`. |
| `redact` listed twice | `Invalid`, when the instance is built | List it once. |
| A layer inside returns something that is not an SDK record | `Unsupported`. Nothing is returned. | Fix the plugin that produced it. |
