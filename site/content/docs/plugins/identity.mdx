`identity()` from `outbound-sdk/identity` links the same person across tools and campaigns. It adds `personKey` and `personKeys` to every lead, and `outbound.person(identifier)`, which returns every record for that person and one timeline of their messages. A key comes from an exact identifier only: a lowercased email address or a cleaned LinkedIn profile URL. There is no matching on names or companies. Records are linked, never merged: each keeps its own `provider`, `workspaceId` and fields.

## Options

`identity()` takes no options.

`outbound.person(identifier, options?)` takes:

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `campaignIds` | `string[]` | none | Look only in these campaigns (refs). Each campaign's leads are walked in full. |
| `timeline` | `boolean` | `true` | `false` leaves the timeline out, which saves one read per matching record. |
| `include` | `("body")[]` | none | `["body"]` asks for message text on the timeline. Without it `bodyText` is `null`. Needs the `messages.body` capability. |

`identifier` is a person key (`email:...` or `linkedin:...`), an email address or a LinkedIn profile URL. Anything else throws `Invalid`.

## How a key is built

| Source | Key | Rule |
| --- | --- | --- |
| `email` | `email:jane.doe@example.com` | Trimmed and lowercased. A value with no `@` gives no key. |
| `linkedinUrl` | `linkedin:jane-doe-example` | The profile slug from the URL, as `profileSlug` from `outbound-sdk` returns it. A URL with no slug gives no key. |

`personKeys` holds every key a lead has, email first. `personKey` is the first of them, or `null` for a lead with neither identifier. The subpath also exports the functions themselves: `emailKey`, `linkedinKey`, `keysOf` and `toKey`.

## What it adds

| Member | Returns |
| --- | --- |
| Every lead | `personKey: string \| null` and `personKeys: string[]`, added at run time. The exported `PersonLead` type describes the result, but `Lead` does not declare the fields, so read them with an `in` check. |
| `outbound.person(identifier, options?)` | A `Person`. |

A `Person` has:

| Field | Meaning |
| --- | --- |
| `key` | The key that was looked up. |
| `keys` | Every key found on the matching records, sorted. |
| `found` | `false` when no record carries the key. The link is unknown, not proven absent. |
| `records` | One lead record per tool or campaign the person is in. |
| `links` | One entry per tool on the instance: `identifiers` (the identifier types it fills on its leads, `email` and `linkedin`), `searchable` (those the vendor itself fills, so it can be asked for a person by them) and `status`. `linked` means it holds a record for the person, `absent` means it can be searched by one of the person's identifier types and no record carries it, and `undetermined` means it can be searched by none of them, so whether the person is in it cannot be told. |
| `timeline` | Every message to and from the person across those records, each once, oldest first. Automatic replies are kept and carry `isAuto`. Empty when `timeline` is `false` or the adapter does not declare `leads.timeline`. |
| `requests` | Vendor requests the lookup made, every lookup and timeline read counted. |

## How the lookup reads

`person()` picks one of three paths from the instance's capabilities:

1. **The vendor can find a lead by identifier** (`leads.lookup`), and `campaignIds` is not set. It asks for the person by each key. A record that carries a second key is looked up under that one too, so an email can lead to a profile and back. The vendor's own matching is not trusted: only a record whose exact key matches is kept.
2. **Otherwise, the adapter lists all leads** (`leads.list`), and `campaignIds` is not set. Every lead is walked.
3. **Otherwise**, every campaign is listed and each campaign's leads are walked. With `campaignIds`, only those campaigns.

On paths 2 and 3, a record that links a new key causes one more full walk, to catch records seen earlier under the other key.

Paths 2 and 3 read every lead they cover. On a large account that is many requests: pass `campaignIds`, or set `maxRequestsPerCall` on the instance.

The timeline is one `lead(ref).timeline()` read per distinct record ref, all started together. A vendor that uses one lead id in every campaign is read once, and a message two reads both return is kept once.

## What a tool can be linked by

`outbound.identifiers()` says, with no request, which identifier types each tool on the instance fills on its leads, and `shared` lists the types two or more tools fill. With `shared` empty, no person can be linked across tools, so an overlap of 0 means the link cannot be told, not that nobody is in both. Instantly has no LinkedIn profile field and can be searched by `email` only, which HeyReach fills only for leads it has enriched. Without any setting, a lead's custom field whose name is `linkedin`, `linkedin url`, `linkedin profile` or `linkedin profile url` (case, spaces, underscores and hyphens ignored, so `LinkedIn_URL` and `linkedin_profile` match) fills `linkedinUrl` when its value is a linkedin.com/in/ URL, graded `derived`. An explicit `leadFields.linkedinUrl` (in code, `OUTBOUND_LEAD_FIELDS` or the CLI's config file) replaces those names. A profile read from a custom field is on the lead, and links it to a LinkedIn tool once the person is found by email, but the vendor cannot be asked for it: it is in `identifiers`, not `searchable`.

`leadIdentifierCoverage(leads)` counts the same from leads you already read: per tool, how many leads carry each type, and which types leads of two or more tools actually carry. A field a tool declares can still be empty on every lead.

## What it changes

It changes no capability and nothing in `meta`.

## With other plugins

List it after `redact` and before `cache`.

With [`redact`](/docs/plugins/redact#with-other-plugins) on the same instance:

- `personKey` and `personKeys` are masked with the field they came from. A key keeps its `email:` or `linkedin:` prefix, and with `strategy: "hash"` the same person still gets the same key.
- `person()` is refused as `Unsupported` while `redact` masks `email` or `linkedin`. It links records by those identifiers, and on masked records it would link nothing. It never answers `found: false` for that reason.

`person()` reads through the instance's public API, so `cache`, `budget`, `audit` and `failover` apply to every read it makes.

| What happened | What you get | What to do |
| --- | --- | --- |
| The identifier is a name or other text | `Invalid`, before any read | Pass an email address, a profile URL or a key. |
| No record carries the key | `found: false`, empty `records` and `timeline` | Treat it as unknown. The person may exist under an identifier the vendor did not give you. |
| A tool can be searched by none of the person's identifier types | Its entry in `links` is `undetermined` | Read it as "can't tell", never as "not there". Look the person up by an identifier that tool can be searched by, such as their email. |
| `redact` on the instance masks `email` or `linkedin` | `Unsupported`, before any read. The message names the plugin. | Use an instance without `redact`, or leave both fields out of its `fields`. |
| The adapter cannot read a lead's timeline | Records link, `timeline` is empty | Check `outbound.capabilities["leads.timeline"]` before relying on the timeline. |
| A read fails part way | `person()` throws that error. No partial answer is returned. | Retry, or bound the lookup with `campaignIds`. |
