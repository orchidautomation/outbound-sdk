`sync({ checkpoints })` from `outbound-sdk/sync` adds `outbound.sync.run(collection, { onPage })`, for scheduled runs that keep your copy of a collection in step. It hands you each page and keeps one checkpoint per collection in a store you supply. The checkpoint holds a cursor, so a run that dies restarts on the page it was reading, and the start time of the last finished run, so the next run asks only for newer records. The SDK stores nothing itself and writes nothing to your database: `onPage` is where you do that.

## Options

`sync(options)`:

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `checkpoints` | `CheckpointStore` | required | Where checkpoints are kept. |
| `overlapMinutes` | `number` | `5` | How far each run reaches back before the start of the last finished one, because records can land while a listing is being read. |
| `now` | `() => number` | `Date.now` | The clock, for tests. |

`outbound.sync.run(collection, options)`:

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `collection` | `"campaigns" \| "leads" \| "messages" \| "replies" \| "senders"` | required | What to walk. |
| `onPage` | `(items, page) => void \| Promise<void>` | required | Receives each page, and `page.campaignRef`: the ref of the campaign it was read for, `undefined` for a page of the whole workspace. The checkpoint moves only after it resolves. |
| `campaignId` | `string` | none | Sync one campaign's records. Not used for `campaigns`. It has its own checkpoint. Not with a campaign scope. |
| `campaign_ids`, `tag`, `campaign_name` | as on [insights](/docs/insights#campaign-scope) | none | Sync only the campaigns of a [campaign scope](#campaign-scope). |
| `resolved` | what `resolveScope` returned | none | Sync the campaigns of a scope found once, so a run per collection does not find them again. Not with `campaignId` or a scope. |
| `maxPages` | `number` | none | Stop after this many pages. The next run resumes from the checkpoint. |
| `limit` | `number` | the adapter's | Records per page, as a hint the adapter may clamp. |

`run` is generic in the record type. Name it at the call site, as the sample does with `run<Lead>`, so `onPage` receives typed records. The name is not checked against `collection`.

## What it adds

| Member | Returns |
| --- | --- |
| `outbound.sync.run(collection, options)` | A `SyncResult`. |
| `outbound.sync.reset(collection, campaignId?)` | Deletes that checkpoint, so the next run starts over. |

A `SyncResult` has:

| Field | Meaning |
| --- | --- |
| `collection` | The collection that was walked. |
| `records`, `pages` | What this run delivered to `onPage`. |
| `resumed` | `true` when this run continued one that had not finished. |
| `since` | The lower bound this run asked for: a creation time, so a record created before it and changed since is not read. `undefined` on a first run, and for a collection that cannot be filtered by date. |
| `complete` | `false` when the run stopped at `maxPages` with more to read. |
| `requests`, `throttledMs` | The vendor requests this run made and the milliseconds it waited for the rate budget. |
| `inboxLeftOut` | Replies and messages tied to no campaign, such as HeyReach's inbox conversations, that the run did not reach: `null` with a note when some were left out, because counting them would read the whole inbox, and `0` where the tool has no such inbox or the run reached it. A run of the whole workspace leaves out only replies, because it reads them as `replies.list` does, without `includeInbox`; sync `messages` to get the inbox's conversations. A campaign's run, or one under a scope, leaves out both. |
| `filter` | Who applied `since`: `"server"` the vendor, so only newer records were read; `"client"` the SDK, after reading every record, so the run cost as much as a full one; `"none"` when no date filter applied. |
| `scope` | Under a campaign scope: `meta`, how its campaigns were found, as `resolveScope` returns it, and `campaigns`, each campaign's `campaignRef`, `name`, `records`, `pages` and `complete`. `since` is then the earliest lower bound of any campaign. |
| `notes` | What to know about the run. A `"client"` run says what it cost, for example "instantly cannot filter leads by date, so this run read every record (2295 requests) and kept the 7 created since …". |

## How a run moves

1. It reads the checkpoint. A `cursor` means an earlier run did not finish, and this one starts from that page.
2. For `leads`, `messages` and `replies`, when the instance can filter that collection by date (`leads.since`, `messages.since`, `replies.since` is not `false`), it asks for records since the checkpoint's `since` minus the overlap. `campaigns` and `senders` are always read in full.
3. Each time a page has been handed out in full, it awaits `onPage`, then saves the cursor for the next page.
4. When the listing ends, it replaces the checkpoint with `{ since }`, set to when this run started. A run that resumed keeps the start time of the run it continued.

Three consequences:

- **A page can be delivered twice.** A crash between `onPage` and the checkpoint write, and the overlap, both replay records. Write with an upsert keyed on `ref`.
- **An incremental run is not a change feed.** It asks for records since a time. Where the SDK applies that filter itself, it compares a lead's `createdAt` and a message's `sentAt`, so a lead whose status changed later is not picked up. A deleted record is never reported. Call `reset` for a full pass, and use [`reconcile`](/docs/plugins/reconcile) to find deletions.
- **The first run reads everything.**
- **Where the SDK filters, every run is a full walk.** Instantly's leads are one case (`leads.since` is `"client"`): the result's `filter` is `"client"`, and its `requests` and `notes` say what the run cost. Check `filter` before you schedule a run every few minutes.

So plan two cadences: incremental runs as often as you need new records, and a `reset` followed by a full run, daily or weekly, to pick up changed statuses and replied flags. A run that the SDK filters costs about as much as that full run, so on such a collection schedule only full runs.

## Campaign scope

`run` takes the campaign scope every insight takes: `campaign_ids`, `tag` and `campaign_name`, so one client's campaigns in a shared workspace sync in one call. The scope's campaigns are found first, as an insight finds them: ids read by id with no listing, a tag or name sent to the vendor where it filters its listing and matched here otherwise. Then each campaign is synced in turn with its own checkpoint, keyed by its `ref`, so no record of another campaign is read. `maxPages` counts pages across all of them, and the next run resumes each campaign where it stopped.

- `campaigns` under a scope is the scope's campaigns, as one page.
- `senders` hands out a sender of several campaigns once per run.
- Replies and messages tied to no campaign, such as HeyReach's inbox conversations, are not reached: a conversation does not name its campaign, so it cannot be matched to the scope. `inboxLeftOut`, and `scope.inboxLeftOut` with it, is `null` with a note where the tool has such an inbox, because counting it would read every campaign's conversations, and `0` where it has none.
- A tag where campaigns carry no tags, such as HeyReach's, is `Unsupported`, and a malformed scope or one given with `campaignId` `Invalid`, before any request.
- `reset(collection, campaignRef)` forgets one campaign's checkpoint.
- A campaign synced before with its bare vendor id as `campaignId` has its checkpoint under that id, not its ref, so the first scoped run walks it again from the start.

To sync several collections of one scope, find its campaigns once with `resolveScope` and pass them as `resolved`. The runs then make no request to find them, their `requests` leave out what finding them cost, and their `scope.meta` is the one you passed.

`run` accepts a `resolved` when its `campaigns` is an array and its `meta.provider` and `meta.workspaceId` are this instance's. Nothing else is checked, and the campaigns are not looked up again, so a list you filtered or reordered is synced as it is. A `resolved` of another provider or workspace, or one with no `campaigns` list, is `Invalid`, before any request.

Campaigns sync in the order of `resolved.campaigns`, one after another, and `scope.campaigns` lists them in that order. With a scope given to `run` directly, the order is the one `resolveScope` returns. To choose it, such as active campaigns first, reorder the list and pass it as `resolved`. With `maxPages`, the campaigns first in the list are the ones read first.

To mean every campaign of the workspace, use `campaign_name: "*"`. It is a glob that matches any name, a campaign with no name included, and it is the supported way to ask for all campaigns, in `run` and `resolveScope` alike. A run with it is still a scoped run: each campaign has its own checkpoint, and replies and messages tied to no campaign are left out, as `inboxLeftOut` says.

`resolveScope(outbound, scope)` from `outbound-sdk` returns the same campaigns, every state, for a caller that reads them itself. Its `meta` gives the requests made, the `evidence`, the scope in words, `notes`, and `tools`: for each tool, how many campaigns matched and its `filter`, which is `id` (read by id), `vendor` (the vendor's listing filter), `here` (a whole listing matched here, still `exact`), `both`, or `none` (a tool whose campaigns carry no tags).

## The store

A checkpoint store is three async functions. A checkpoint is a small JSON object with up to four strings: `cursor`, `since`, `startedAt` and, for one campaign's checkpoint, `campaignRef`, the campaign's ref, so a store can keep one row per campaign.

| Function | Called |
| --- | --- |
| `get(key)` | Once at the start of each run. Return `undefined` when there is none. |
| `set(key, checkpoint)` | After every page, and once when the run finishes. |
| `delete(key)` | By `sync.reset`. |

The key is `outbound-sync:` followed by a hash of the instance's provider, workspace label, the collection and the `campaignId`. Two instances with the same provider and workspace label share checkpoints, which is what lets a new process resume.

`memoryCheckpointStore()` keeps checkpoints in this process's memory. It is meant for tests and one-off scripts: a checkpoint that does not outlive the process cannot resume anything.

## What it changes

It changes no capability, no record and nothing in `meta`. It has no layer of its own, so its position in `plugins` does not matter.

## With other plugins

`run` reads through the instance's public API, so every layer applies to the pages it delivers.

- With `redact`, `onPage` receives masked records.
- With `cache`, a page can be served from the store. Leave the list operations out of the cache (`only`) on an instance you sync from, or give the sync its own instance.
- A `budget` or `maxRequests` cap that stops a run leaves the checkpoint at the last page that was handled. The next run resumes there.

| What happened | What you get | What to do |
| --- | --- | --- |
| `onPage` throws or rejects | `run` rejects with that error. The checkpoint is still before the page. | Fix the cause and run again. The page is delivered again. |
| A vendor read fails part way | `run` rejects with the `OutboundError`. Pages already handled are checkpointed. | Run again. It resumes. |
| The adapter cannot filter the collection by date | Every run reads the whole collection. `since` in the result is `undefined`. | Expect the cost of a full walk each time, and upsert. |
| The adapter filters by date only after reading (`"client"`) | Only the newer records reach `onPage`, but every page is read. `filter` is `"client"`, and `notes` gives the cost. | Treat it as a full run when you schedule it. |
| The adapter cannot list the collection | `Unsupported`, before any request | Sync a collection the adapter declares. |
| The name is not one of the five collections | `Invalid`, before any read and before the checkpoint is touched. `reset` refuses it too. | Fix the name. Code without types can pass any string. |
| The store rejects | `run` rejects with the store's error | Run again once the store is back. |
