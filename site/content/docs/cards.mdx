`outbound-sdk/cards` turns every tool and insight answer into a card: a headline, a few numbers, a table and a chart, ready to post in Slack or draw in an app.

A card is built from the numbers the tool returned. No model writes it, so a number on a card is the number that was read, and a count the vendor does not report is a dash, never a zero. The package adds no dependency.

This page uses the [in-memory adapter](/docs/adapters/memory). The Slack output was posted to a Slack developer sandbox and accepted; how far each real adapter has been checked is on [what is verified](/docs/status).

## Draw a card and post it to Slack

`cardFor(name, result)` takes a tool's name and its result. `toSlackMessage(card)` returns `{ text, blocks }` for `chat.postMessage` or an incoming webhook.

`cardFor` never throws. A failed result becomes a card that says what failed, and a tool of your own with no card gets one that lists its plain values.

## The card format

A card is a [json-render](https://json-render.dev) spec for the chat catalog (`@json-render/chat`): a flat map of elements under a root `Card`, using `Text`, `Fields`, `Table`, `Chart`, `Divider` and `Actions`.

<include meta='title="spec.ts"'>../_examples/cards/spec.ts</include>

<include lang="text" meta='title="Output"'>

</include>

One spec goes to four places:

| Where | How |
| --- | --- |
| Slack, with no package | `toSlackMessage(card)` or `toSlackBlocks(card)` |
| Slack, Teams, Discord and Google Chat through [Chat SDK](https://chat-sdk.dev) | `thread.post(toCard(card))`, with `toCard` from `@json-render/chat` |
| A web app | any json-render renderer with a registry for those components |
| An agent that composes its own layout | give it the catalog, and the tool results as data |

`toSlackBlocks` writes the same blocks Chat SDK's Slack adapter writes for the same card. The test suite holds every card to both: the json-render chat catalog must accept the spec inside Slack's limits, and the two block lists must be equal.

## What each card shows

Every [tool](/docs/tools) and every [insight](/docs/insights) has a card; `CARD_NAMES` lists them. Each one has the same parts, in the same order:

- **A finding.** The one sentence to read if nothing else is read. A check that had nothing to read says so; it does not show green.
- **Numbers.** Up to twenty, as label and value.
- **A list or a table.** Cut to eight rows, with a line saying how many more there are. The `maxRows` option changes the cut.
- **A chart**, where the answer has a series or a split: reply rate by campaign, replies by weekday, a count per day.
- **The source.** The evidence level, the provider and the number of vendor requests, then the insight's notes. A read a cap stopped early is marked incomplete.

The `links` option adds link buttons under a card, five at most, for example to the campaign in the vendor's app. The SDK is read-only, so a card has link buttons and nothing that writes.

## Text from prospects

A reply can contain `<!channel>`, a link or an instruction. Every string a card takes from a vendor or a prospect is made inert first: angle brackets become look-alikes, a markdown link loses its join, a code fence is broken and `@channel`, `@here` and `@everyone` are split. `safe` is exported for text you add yourself.

Message text is shown only when it was asked for (`include_bodies` on the tool, `includeText` on `eventCard`), as a quote, cut short, with a note that it is data. The raw response of `vendor_read` is never drawn. See [untrusted content](/docs/tools/untrusted-content).

## From the command line

[`outbound tool`](/docs/cli) and `outbound insight` take `--card` to print the answer's card and `--slack` to print it as a Slack message:

```sh
outbound insight bounce_watch --slack --compact \
  | curl -X POST -H 'content-type: application/json' -d @- "$SLACK_WEBHOOK_URL"
```
