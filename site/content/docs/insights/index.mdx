`outbound-sdk/insights` answers the questions operators ask, computed from the normalized reads. Each insight is one typed method, one agent tool and one CLI command. It calls no AI model, stores nothing and never writes to a vendor. Every number is a count, a rate or a textbook test you can check by hand.

How far each adapter has been checked against a live account is on [what is verified](/docs/status).

## Set it up

Add the plugin. Every insight becomes a method on `outbound.insights`.

The plugin makes no request by itself. An insight reads through the instance, so the vendor's rate limit, your `maxRequests` and every other plugin apply to it. See [rate limits](/docs/rate-limits).

## What every answer carries

Every insight returns the same three parts: its tool name in `insight`, the answer in `data`, and `meta`.

| Field | What it holds |
| --- | --- |
| `data` | The answer. Its type is exported under the insight's name: `CampaignRanking`, `PersonSummary` and so on. |
| `meta.requests` | Vendor requests the insight made. The in-memory adapter makes none, so the samples on this site show 0. |
| `meta.complete` | `false` when a cap stopped a read early, so the answer covers part of the data. |
| `meta.evidence` | `exact` only when every read behind the answer was exact. Otherwise the weakest of them: `sampled`, then `derived`. |
| `meta.notes` | What to know before trusting the numbers: which cap was reached, or a part that was skipped because the adapter cannot read it. |
| `meta.computedAt` | When the insight ran, ISO 8601 UTC. |
| `meta.provider` | The adapter's name. |

Pass `meta.notes` on with the numbers. An answer cut short by a cap looks like a whole answer unless you say so.

## Caps

Every read an insight makes has a cap you can set. The defaults keep one call to tens of requests on a real vendor. When a cap stops a read, `meta.complete` is `false` and a note names the input to raise, for example "Stopped at 25 campaigns (max_campaigns); more exist." The answer is never padded or guessed.

| Cap | Default | Where |
| --- | --- | --- |
| `max_campaigns` | 20 | The [people](/docs/insights/people) insights and `copyReuse`, apart from `leadCollisions` and `suppressionCheck` |
| `max_campaigns` | 200 | `leadCollisions`, `suppressionCheck`: every campaign in the statuses |
| `max_campaigns` | 25 | `settingsAudit` |
| `max_campaigns` | 50 | `bounceWatch`, `senderCapacity`, `senderLoad` and the [operations](/docs/insights/operations) insights that list campaigns, apart from `channelMix` |
| `max_campaigns` | 150 | `channelMix` |
| `max_leads` | 500 | `personalizationGaps` |
| `max_leads` | 1,000 | `accountSummary` |
| `max_leads` | 2,000 | `hotLeads`, `pipelineForecast`, `campaignDiagnosis` |
| `max_leads_per_campaign` | 500 | `clientReport` |
| `max_leads_per_campaign` | 1,000 | `leadCollisions`, `suppressionCheck` |
| `max_block_entries` | 10,000 | `suppressionCheck` |
| `max_replies` | `null`: the whole window, up to 2,000 | `droppedReplies` |
| `max_messages` | 2,000 | `replyTiming` |
| `max_senders` | 50 | `domainHealth` |
| `max_senders` | 500 | `campaignDiagnosis` |
| `max_senders` | 1,000 | `warmupReadiness`, `senderCapacity`, `senderLoad` |

The range of each cap is on the insight's own section.

An insight that reads campaigns in some states, active by default, and finds none in them checked nothing. Its answer has `meta.complete` set to `false` and a note that counts the campaigns there are, for example "No campaign is active, so nothing was checked (18 campaigns: 8 completed, 10 draft). Pass statuses to check the others." Finding those costs one more page of campaigns. A workspace with no campaigns at all is a complete, empty answer. Thresholds (a bounce rate that is too high, a warmup score that is too low) are inputs with defaults too.

`maxRequestsPerCall` on `createOutbound` is a different limit. It is the most vendor requests one call may make, and a call that reaches it fails with `RateLimited` instead of returning part of an answer.

## Request caps

Each insight also has a cap on the vendor requests the whole run may send, retries included, counted across every read it makes, even reads that run side by side. You do not have to set one.

Each insight states what it costs as arithmetic over the reads it makes and the costs the adapter declares. That cost is worked out twice for the input you pass: at the least every read can cost, and at the most, with every `max_*` cap in the input reached.

- **The default cap** is the most, a quarter more for retries (each retry is a request) and 20 on top. An insight that works at its inputs today is not stopped by its default.
- **`maxRequests`**, the second argument's option, replaces the default: `outbound.insights.clientReport({}, { maxRequests: 100 })`. `maxRequests: Infinity` removes the default. A `maxRequestsPerCall` on the instance and a [`budget()`](/docs/plugins/budget) still apply under it, and the lowest cap stops the run.
- **`insightCost(outbound, name, input)`** returns `{ min, max, defaultCap }` for an input, or `null` where the cost is unknown.

A `-` is an insight that adapter cannot serve. `bounceWatch`, `clientReport`, `leadCollisions`, `senderCapacity`, `senderLoad` and `suppressionCheck` are the ones whose default inputs can cost more than an [insight tool call](/docs/tools#request-caps) may spend, 500 requests: for `bounceWatch`, 50 campaigns, each over the bounce rate with 10 senders to read, is about 600; for `clientReport` on Instantly, each stats read also reads the campaign's [tracking settings](/docs/api/stats#opens-and-clicks-that-were-not-measured); for `senderCapacity` and `senderLoad` on Instantly, each campaign's senders are found by paging through every mailbox of the workspace, 2 requests a page, so the most counts 1,000 mailboxes for each of 50 campaigns. A workspace of 303 mailboxes and 24 active campaigns takes about 230. Such a tool call stops at 500, and its result names the `max_campaigns` to ask for. `leadCollisions` and `suppressionCheck` read every campaign in the statuses by default, so their most is 200 campaigns of 1,000 leads; a workspace of 24 active campaigns takes a few hundred requests, and a call stopped at 500 leads with what it checked and gives no total.

### Refused before the first request

An insight whose **least** cost for the input is over its cap, or over what a `budget({ per: "run" })` has left, is refused before it sends anything: `RateLimited`, `limit: "call"`, `permanent: true`, with the least, the most, the cap and the input to lower. The check uses the lower bound on purpose. The most an input can cost assumes every cap is reached, which a small workspace never comes near, so refusing on it would turn away calls that fit.

An insight that lists campaigns checks again once the listing is read. The number of campaigns is then known, so the least is closer to the truth, and a run that cannot afford even that stops there, having spent only the listing. The message has the same form.

Where the adapter declares no costs, as a [combined](/docs/adapters/combine) instance does, nothing is checked and there is no default cap: the run behaves as it always has. Scope it with `outbound.workspace(id)` to get both.

### Stopped part way

A run that reaches a request cap part way stops before the next request. The cap can be the insight's own, a `budget()` or `maxRequestsPerCall` on the instance.

An insight whose answer still means something over part of the data returns what it read: `senderCapacity`, `senderLoad`, `periodComparison`, `campaignRanking`, `clientReport` and `hotLeads`. The answer comes back with `meta.complete: false`, `meta.requests` at the cap, and a note that names the cap, what raises it and how much was read, such as `Stopped after 141 requests, at its default cap of 141 requests for this input. Pass maxRequests to raise it (Infinity removes the default). Read 18 of 24 active campaigns; the answer covers those.` A campaign whose own reads the cap cut off is left out, never counted with part of its data. A listing the cap cut short counts as capped, so `hotLeads` still looks for the leads behind recent replies. A `campaign` given by name is the exception: the lookup must see every campaign, because a name found on part of them could belong to another, so a cap that stops it fails the run with `RateLimited`. The reads that cover the whole workspace, such as its totals or its unusual days, are made before the per-campaign reads, so they stay in the answer.

Any other insight fails with `RateLimited`, `limit: "call"`, the requests it sent and the input to lower. An insight that counts a failed read as unchecked, such as `droppedReplies`, finishes instead, with `meta.complete: false` and a note naming the cap.

The messages name the setting of the surface you use: `maxRequests` in the SDK, `maxRequestsPerToolCall` for an insight tool, and `--max-requests` in the CLI and on `outbound mcp`. In the CLI, `--max-requests` replaces an insight's default cap as well as capping the command.

Costs are read from the adapter's declared costs, which state the usual case. A read that costs more than declared (a custom lead label on Instantly, for example) is in the margin; a thread or timeline is priced as one page.

## Counts that are null

A count a vendor does not report is `null`, never `0`, and so is every rate built on it. An insight sets such a record apart and says why. It does not rank it last or count it as clean.

### What every number carries

Every insight and every [tool](/docs/tools) holds its numbers to one contract, so an agent cannot read a gap as a zero:

- **Zero is a count the vendor reported as 0.** It is never a stand-in for a missing count, a record that was not read or a rate with nothing to divide by.
- **Missing is `null`, with a reason.** The reason is in `meta.notes`, or beside the value where a record carries its own (`reason`, `unknown`, `notChecked`). The [adapter pages](/docs/adapters) say which fields a vendor never reports.
- **Unchecked is counted on its own.** A record that could not be checked, such as a conversation `droppedReplies` could not read or a sender `deliverability_check` did not check, is counted apart (`totals.unchecked`, `coverage.notChecked`), never as clean or as 0, and the answer has `meta.complete: false`.
- **Stale is told by a time.** Nothing is stored between calls, so a number carries the time it is as of: `meta.computedAt` on every answer, and the vendor's own time where it reports one (`checkedAt` on a sender's health, `lastRepliedAt` on a lead). An insight that judges age says so in its answer, as `hotLeads` counts `totals.stale`.
- **The source is named.** Every answer has `meta.provider` and `meta.evidence`, and every record its `provider`, `workspaceId` and `ref`.
- **Coverage is stated.** `meta.complete: false` means the answer covers part of the data, a cap or a record left unchecked, and a note says which part. A rate over several campaigns counts only those that report both of its sides, and a note names it when it leaves some out.
- **The window is in the answer**: `period`, `current` and `previous`, or `since`. A tool that takes `from` and `to` gives back the `period` it read, `null` for an open end.
- **A rate carries its denominator.** It is `{ count, of, rate, low, high }`, and `replyRateBasis` says whether `of` counts leads contacted or messages sent. It is the same for every campaign in one answer, so leads and sends are never added into one `of`. A tool row puts a rate next to the counts it divides, such as `bounceRate` beside `bounced` and `sent`.

## The two tests behind the numbers

**The Wilson interval.** A rate from a small sample is a weak claim: 2 replies from 10 sends and 200 from 1,000 are both 20%, but only the second tells you much. Wherever an insight reports a rate that rests on a sample, it also reports the 95% Wilson score interval, the range the true rate plausibly lies in. Rankings sort by the low end of that interval (the high end for a bounce rate), so a lucky small campaign cannot outrank a proven large one.

**The two-proportion test.** When an insight compares two rates (this week against last, variant A against B, email against LinkedIn), it runs a two-proportion z-test and reports the p-value: the chance of a gap at least this large if the two rates were in fact equal. Under `alpha` (an input, default 0.05) the insight calls the difference "more than chance". Over it, the insight says the gap could be chance. It never calls a winner on the raw rates alone.

Both are exported, with the other arithmetic the insights share.

## Inputs are checked

An input is checked twice: by the method's type when you compile, and by the insight's schema when it runs. The method's type is generated from the schema, so hovering a field such as `max_leads` in an editor shows its default and its range. `InsightInputs["hotLeads"]` is that type, for code that builds an input before calling. A key the insight does not take is refused as `Invalid`, with the list of inputs it does take. It is never dropped, because a dropped filter would quietly answer a wider question than the one asked. A missing required input is refused as `Invalid` too, for example ``step_funnel: `campaign` is required``. A `campaign` that does not exist is refused as `NotFound`, for the same reason: an empty campaign would answer as "nothing happened".

An insight that needs a capability the adapter lacks, or a field its records never fill (`tagRollup` on campaigns with no tags), is refused as `Unsupported` before any request is made, and is left out of the tool list, so a model is never offered a tool that cannot work. So is an insight that matches records by a field the [`redact` plugin](/docs/plugins/redact) masks, such as `accountSummary` while emails are masked. A tool's `next` hint never names a tool that is not on offer.

## Campaign scope

Every insight takes three more inputs that say which campaigns of the workspace it may read, such as one client's in an agency workspace:

| Input | Reads only the campaigns |
| --- | --- |
| `campaign_ids` | With these ids, each a `ref` or the vendor's id, up to 500. They are read one by one, with no campaign listing. |
| `tag` | That carry this tag, ignoring case. Refused as `Unsupported` before any request where campaigns carry no tags (`campaigns.byTag` is `false`, such as HeyReach). |
| `campaign_name` | Whose whole name matches, ignoring case: an exact name (`Acme Q4`), a glob with `*` and `?` (`Acme*`), or `/regex/` with flags `i`, `m`, `s` or `u`. A regex ignores case only with `i`. |

Given together, a campaign must match every one, and the insight's own filters, such as `statuses`, narrow it further. The scope is applied once the campaigns are found and before any per-campaign read. Where the vendor can filter its listing, by tag or by name (`campaigns.byTag` or `campaigns.byName` is `server`), it is asked to. Elsewhere the listing is read and filtered here. Either way `meta.notes` says how many campaigns matched and which side filtered. A malformed scope, such as an empty list or a regex that does not compile, is refused as `Invalid` before any request.

Under a scope an insight never reads another campaign's rows. A `campaign` input outside the scope is refused. Replies, senders and leads are read campaign by campaign. Replies that belong to no campaign are left out, and so are reads that only exist for the whole workspace, such as `client_report`'s unusual days. Workspace totals are the scope's campaigns added up, as `derived`, so a lead in two of them counts in both. Each of these says so in `meta.notes`.

## Names

The same word means the same thing in every insight.

- **Inputs are snake case, answers are camel case.** `max_campaigns` goes in and `moreCampaignsExist` comes out, because the same input schema serves the method, the agent tool and the CLI. The [built-in tools](/docs/tools) follow the same rule: snake case inputs and camel case answers.
- **`from` and `to` are an inclusive range of `YYYY-MM-DD` days.** `null`, the default, is no bound: the whole history, or up to today. A day that does not exist, such as `2026-02-30`, is refused.
- **`since` is an ISO time** that a listing starts at, as in `droppedReplies` and `replyTiming`.
- **`days` is the last N complete days, ending yesterday.**
- **`limit` is how many items come back. `max_*` caps what is read.** `max_leads` caps every lead read; `max_leads_per_campaign` caps each campaign's.
- **`max_<metric>_rate` and `min_<metric>_rate` are cutoffs**, such as `max_bounce_rate`. `anomalies`' `threshold` is a z-score, not a rate, and keeps its name, as do `recency_days` (how fast `hotLeads` lets a reply fade) and `baseline_days`.
- **`campaign` in an answer is always the campaign's ref**, even when you passed its bare vendor id, and a campaign row carries `campaignName` beside it.
- **A step is `stepIndex` and `stepNumber`.** `stepIndex` counts from 0, as vendors and the records' `stepIndex` do: the first email is 0. `stepNumber` counts from 1, as a person does: the first email is step 1. Every sentence and card says the step number, as "step 2 (of 4)" when the sequence's length is known. A field that names one step does the same with a suffix (`topStepIndex` and `topStepNumber`), and a list of steps is `…StepIndexes` and `…StepNumbers`.
- **A rate is `{ count, of, rate, low, high }`**: the count, what it is divided by, the rate and the ends of its 95% Wilson interval. A few figures stay plain numbers: `PeriodNumbers`' rates, whose count and denominator are in the comparison's `rates`, and `personSummary`'s `campaignReplyRate` and `personalizationGaps`' `affectedRate`, which no single count is behind.

Names that broke this rule before 0.4.0 were renamed in 0.4.0 and the old names were removed in 0.6.0. An old input name is now `Invalid`, and the message lists the inputs the insight takes.

| Insight | Old input | New input |
| --- | --- | --- |
| `bounceWatch` | `threshold` | `max_bounce_rate` |
| `domainHealth` | `spam_rate_threshold` | `max_spam_rate` |
| `campaignDiagnosis` | `recent_days` | `days` |
| `clientReport` | `top` | `limit` (the `top` list in the answer keeps its name) |

The old answer fields were removed in 0.6.0 too. Read `campaignName` for `name`, `low`, `high` and `of` for `interval` and `trials`, `rates.replyRate` for `replyRate`, `replyRateInterval` and `replyRateBasis`, `rate` for `spamRate`, and bounceWatch's `maxBounceRate` for `threshold`. [Cards](/docs/cards) read only the new fields, so a result stored before 0.4.0 does not show what only an old field held.

A bare step number meant a count from 0 in the data and a count from 1 in sentences, so it was misread. From the next minor release each answer carries both numbers; the old names keep their old meaning, counted from 0, and are deprecated, to be removed in 0.15.0. Read the new names instead:

| Insight | Deprecated | Read instead |
| --- | --- | --- |
| `stepFunnel` | `step`, `topStep`, `lastStepEarningPlace` | `stepIndex` or `stepNumber`, `topStepIndex` or `topStepNumber`, `lastStepEarningPlaceIndex` or `lastStepEarningPlaceNumber` |
| `personSummary` | `lastStep`, `repliedSteps` | `lastStepIndex` or `lastStepNumber`, `repliedStepIndexes` or `repliedStepNumbers` |
| `variantTest`, `copyAudit`, `copyPreview`, `personalizationGaps` (each use) | `step` | `stepIndex` or `stepNumber` |
| The `winning_steps` tool (each step) | `step` | `stepIndex` or `stepNumber` |

## Run one by name

`runInsightByName` takes the tool name or the method name and JSON input. It is what the CLI and an agent's tool call go through. The answer's `data` is typed as JSON, so use the method when you know the insight at compile time. An unknown name throws `Invalid` and lists the known names.

`listInsights` needs no instance. It returns each insight's `name`, `key`, `description`, `needs` and its input as JSON Schema in `parameters`.

`insightTools(outbound)` returns the insights this instance can serve as agent tools, in the form every wrapper in [`outbound-sdk/tools`](/docs/tools) accepts through `extra`. Pass `only` to offer some of them.

## From the command line

`outbound insight` with no name lists every insight as JSON. With a name it runs one and prints the answer. `--input` takes the same inputs as the method, as JSON.

```sh
outbound insight
outbound insight person_summary --input '{"person":"jane@example.com"}'
outbound insight client_report --input '{}'
```

`outbound tools`, `outbound tool` and `outbound mcp` offer the insights with the other tools, and `outbound person <email or LinkedIn URL>` runs `person_summary`. See [CLI commands](/docs/cli/commands) and [the MCP server](/docs/cli/mcp). These commands are not run by this site's tests.

## Define your own

`defineInsight` takes a name, a description, a Zod object for the input, the capabilities it needs and a `run` function. `runInsight` runs it with the same input checking, capability check and `meta` as the built-in ones, and keeps its typed answer. A definition's `execute` method is the untyped form the tool list uses.

`run` receives a context. Read through its helpers so the cost and the evidence of every read reach `meta`.

Give the definition a `cost` to have a default cap and the check before the first request: `cost: (input, price) => price.one("stats") + price.list("leads.list", input.max_leads)`. `price` has `one(action)`, `list(action, max)`, `walk(action)`, `lookup(max)`, `campaignsIn(statuses, max)`, `campaigns(max)`, `upTo(max)` and `capabilities`; the cost is worked out once at the least each of them can be and once at the most. `scales` names the input a cap message tells the caller to lower. Without `cost` an insight has no default cap. By default a request cap that stops `all` or `each` part way keeps what they read, with `meta.complete: false` and a note, instead of throwing away the requests already spent. Set `partialOnCap: false` when the answer means nothing over part of the data, so the run fails with `RateLimited` instead.

| On the context | What it does |
| --- | --- |
| `outbound` | The instance to read through. |
| `now` | The time the insight runs at, in milliseconds. Use it, not `Date.now()`, so a test can fix the clock with the `now` option of `runInsight`. |
| `rows(stats)` | Records a stats read and returns its rows. |
| `one(item)` | Records one lookup and returns the record. |
| `page(page)` | Records one page and returns its items. An unfinished page marks the answer incomplete. |
| `all(walk, cap)` | Walks a `listAll` to its end or its `max`, and marks the answer incomplete when `max` cut it short. `cap` (`{ max, what, input }`) names what was capped and the input that raises it, for the note. |
| `each(items, read, what)` | Reads each item, a few side by side, and returns the results in order. Unless `partialOnCap` is `false`, an item whose read a request cap stopped is left out and a note says how many of the `what` were read. |
| `note(text)` | Adds a note. The same note is kept once. |
| `partial(reason)` | Marks the answer incomplete, with the reason as a note. |
| `campaignsFound(count)` | Says how many campaigns were found, once they are listed. A run whose least cost for that many is over its cap stops there. The built-in insights call it after their campaign listing. |

The arithmetic is exported from `outbound-sdk/insights` as plain functions:

| Function | Returns |
| --- | --- |
| `rate(part, whole)` | `part / whole`, or `null` when either is unknown or the whole is zero |
| `wilson(successes, trials)` | The 95% Wilson interval as `low` and `high`, or `null` |
| `compareRates(first, second, alpha)` | The two-proportion test: `z`, `pValue`, `significant`. `null` when a side has no trials or both rates are 0 or 1 |
| `total(values)` | The known values added up. `null` when none is known |
| `mean`, `median`, `percentile(values, fraction)` | `null` for an empty list. Percentiles use linear interpolation |
| `deviation(values)` | The sample standard deviation. `null` with fewer than two values |
| `zScore(value, history)` | How many standard deviations `value` sits from the mean of `history`. `null` when the history has no spread |
| `round(value)` | Four decimal places. `null` stays `null` |
| `tally(values)` | How often each value occurs, as a `Map` in first-seen order |

`defineInsight` does not add your insight to `outbound.insights`, `listInsights` or `insightTools`. Those hold the built-in 27.

## Things to know

- **"The last N days" means N complete UTC days ending yesterday**, so a half-finished today cannot read as a drop.
- **Records are linked by exact identifier, never by name.** An email address finds a LinkedIn record only when a tool holds both for that person.
- **Finding a person costs a different number of requests on each vendor:** 1 on Instantly, 2 by profile or about 4 by email on HeyReach, and 1 to 2 on Smartlead.
- **A vendor's thread can be shorter than its sequence.** Instantly's email list does not hold every email a campaign sent, so `personSummary` counts messages sent from the lead's last step when the thread is shorter, and says so in a note.
- **A combined instance reads a conversation by thread id by asking each member that reads threads**, because a thread id is one vendor's own and names no member. A member that cannot take the id holds no such thread; one that can may spend a request finding it empty.
- **`bounceWatch` judges a sender on everything it sent in the period**, not only in the offending campaign: no vendor reports one sender within one campaign.
- **`variantTest` makes no correction for comparing three or more variants**, and its "sends still needed" assumes both rates stay as they are.
- **`anomalies` judges a day against a flat baseline without a z-score.** If every earlier day had the same count, there is no standard deviation to measure against. A day with another count is flagged with `judgedBy: "flat_baseline"` and a `null` `zScore`, whatever `threshold` is.
- **A rate over several campaigns counts only the campaigns that report both sides of it.** `tagRollup`, `channelMix`, `periodComparison` and `clientReport` add counts up across campaigns. A campaign that reports sends but no bounces adds to the sends shown and is left out of the bounce rate, and a note says so.
- **`hotLeads` is a ranking, not a prediction.** Its score is the sum of weighted parts that are returned with it.
- **The findings are sentences built from the numbers by fixed rules.** No model writes them, so the same data always gives the same sentence.
