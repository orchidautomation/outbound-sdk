`outbound-sdk/insights` answers the questions operators ask, computed from the normalized reads. Each insight is one typed method, one agent tool and one CLI command. It calls no AI model, stores nothing and never writes to a vendor. Every number is a count, a rate or a textbook test you can check by hand.

How far each adapter has been checked against a live account is on [what is verified](/docs/status).

## Set it up

Add the plugin. Every insight becomes a method on `outbound.insights`.

The plugin makes no request by itself. An insight reads through the instance, so the vendor's rate limit, your `maxRequests` and every other plugin apply to it. See [rate limits](/docs/rate-limits).

## What every answer carries

Every insight returns the same three parts: its tool name in `insight`, the answer in `data`, and `meta`.

| Field | What it holds |
| --- | --- |
| `data` | The answer. Its type is exported under the insight's name: `CampaignRanking`, `PersonSummary` and so on. |
| `meta.requests` | Vendor requests the insight made. The in-memory adapter makes none, so the samples on this site show 0. |
| `meta.complete` | `false` when a cap stopped a read early, so the answer covers part of the data. |
| `meta.evidence` | `exact` only when every read behind the answer was exact. Otherwise the weakest of them: `sampled`, then `derived`. |
| `meta.notes` | What to know before trusting the numbers: which cap was reached, or a part that was skipped because the adapter cannot read it. |
| `meta.computedAt` | When the insight ran, ISO 8601 UTC. |
| `meta.provider` | The adapter's name. |

Pass `meta.notes` on with the numbers. An answer cut short by a cap looks like a whole answer unless you say so.

## Caps

Every read an insight makes has a cap you can set. The defaults keep one call to tens of requests on a real vendor. When a cap stops a read, `meta.complete` is `false` and a note names the input to raise, for example "Stopped at 25 campaigns (max_campaigns); more exist." The answer is never padded or guessed.

| Cap | Default | Where |
| --- | --- | --- |
| `max_campaigns` | 20 | The [people](/docs/insights/people) insights and `copyReuse` |
| `max_campaigns` | 25 | The [senders](/docs/insights/senders) and [operations](/docs/insights/operations) insights that list campaigns |
| `max_campaigns` | 50 | `bounceWatch` |
| `max_leads` | 500 | `hotLeads`, `personalizationGaps` |
| `max_leads` | 1,000 | `accountSummary` |
| `max_leads` | 2,000 | `pipelineForecast` |
| `max_leads_per_campaign` | 500 | `leadCollisions`, `suppressionCheck`, `clientReport` |
| `max_block_entries` | 2,000 | `suppressionCheck` |
| `max_replies` | 50 | `droppedReplies` |
| `max_messages` | 2,000 | `replyTiming` |
| `max_senders` | 50 | `domainHealth`, `campaignDiagnosis` |
| `max_senders` | 100 | `warmupReadiness` |
| `max_senders` | 200 | `senderCapacity`, `senderLoad` |

The range of each cap is on the insight's own section. Thresholds (a bounce rate that is too high, a warmup score that is too low) are inputs with defaults too.

`maxRequests` on `createOutbound` is a different limit. It is the most vendor requests one call may make, and a call that reaches it fails with `RateLimited` instead of returning part of an answer.

## Counts that are null

A count a vendor does not report is `null`, never `0`, and so is every rate built on it. An insight sets such a record apart and says why. It does not rank it last or count it as clean.

## The two tests behind the numbers

**The Wilson interval.** A rate from a small sample is a weak claim: 2 replies from 10 sends and 200 from 1,000 are both 20%, but only the second tells you much. Wherever an insight reports a rate that rests on a sample, it also reports the 95% Wilson score interval, the range the true rate plausibly lies in. Rankings sort by the low end of that interval (the high end for a bounce rate), so a lucky small campaign cannot outrank a proven large one.

**The two-proportion test.** When an insight compares two rates (this week against last, variant A against B, email against LinkedIn), it runs a two-proportion z-test and reports the p-value: the chance of a gap at least this large if the two rates were in fact equal. Under `alpha` (an input, default 0.05) the insight calls the difference "more than chance". Over it, the insight says the gap could be chance. It never calls a winner on the raw rates alone.

Both are exported, with the other arithmetic the insights share.

## Inputs are checked

An input is checked twice: by the method's type when you compile, and by the insight's schema when it runs. The method's type is generated from the schema, so hovering a field such as `max_leads` in an editor shows its default and its range. `InsightInputs["hotLeads"]` is that type, for code that builds an input before calling. A key the insight does not take is refused as `Invalid`, with the list of inputs it does take. It is never dropped, because a dropped filter would quietly answer a wider question than the one asked. A missing required input is refused as `Invalid` too, for example ``step_funnel: `campaign` is required``. A `campaign` that does not exist is refused as `NotFound`, for the same reason: an empty campaign would answer as "nothing happened".

An insight that needs a capability the adapter lacks, or a field its records never fill (`tagRollup` on campaigns with no tags), is refused as `Unsupported` before any request is made, and is left out of the tool list, so a model is never offered a tool that cannot work. So is an insight that matches records by a field the [`redact` plugin](/docs/plugins/redact) masks, such as `accountSummary` while emails are masked. A tool's `next` hint never names a tool that is not on offer.

## Names

The same word means the same thing in every insight.

- **Inputs are snake case, answers are camel case.** `max_campaigns` goes in and `moreCampaignsExist` comes out, because the same input schema serves the method, the agent tool and the CLI. The [built-in tools](/docs/tools) take snake case inputs too, and answer in snake case JSON written for a model; an insight's answer is camel case wherever it is read.
- **`from` and `to` are an inclusive range of `YYYY-MM-DD` days.** `null`, the default, is no bound: the whole history, or up to today. A day that does not exist, such as `2026-02-30`, is refused.
- **`since` is an ISO time** that a listing starts at, as in `droppedReplies` and `replyTiming`.
- **`days` is the last N complete days, ending yesterday.**
- **`limit` is how many items come back. `max_*` caps what is read.** `max_leads` caps every lead read; `max_leads_per_campaign` caps each campaign's.
- **`max_<metric>_rate` and `min_<metric>_rate` are cutoffs**, such as `max_bounce_rate`. `anomalies`' `threshold` is a z-score, not a rate, and keeps its name, as do `recency_days` (how fast `hotLeads` lets a reply fade) and `baseline_days`.
- **`campaign` in an answer is always the campaign's ref**, even when you passed its bare vendor id, and a campaign row carries `campaignName` beside it.
- **A rate is `{ count, of, rate, low, high }`**: the count, what it is divided by, the rate and the ends of its 95% Wilson interval. A few figures stay plain numbers because no single count is behind them: `PeriodNumbers`' rates, `personSummary`'s `campaignReplyRate` and `personalizationGaps`' `affectedRate`.

Names that broke this rule before 0.3.0 have new ones. The old name still works until 0.4.0: it gives the same answer with a note in `meta.notes`, the tool parameters mark it `deprecated`, and passing both names is `Invalid`.

| Insight | Old input | New input |
| --- | --- | --- |
| `bounceWatch` | `threshold` | `max_bounce_rate` |
| `domainHealth` | `spam_rate_threshold` | `max_spam_rate` |
| `campaignDiagnosis` | `recent_days` | `days` |
| `clientReport` | `top` | `limit` (the `top` list in the answer keeps its name) |

Old answer fields stay beside the new ones, marked `@deprecated` in the types, until 0.4.0: `name` beside `campaignName`, `interval` and `trials` beside `low`, `high` and `of`, `replyRate`, `replyRateInterval` and `replyRateBasis` beside `rates.replyRate`, `spamRate` beside `rate`, and bounceWatch's `threshold` beside `maxBounceRate`. [Cards](/docs/cards) draw either form.

## The insights

The tool and CLI name of each is the same words in snake case: `personSummary` is `person_summary`.

### People and accounts

[Reference](/docs/insights/people)

| Method | Answers | Needs |
| --- | --- | --- |
| `personSummary` | One person across campaigns and channels: messages sent, replies, steps replied to, interest | `leads.lookup`, `leads.timeline` |
| `accountSummary` | Everyone at one company domain, across campaigns and tools | `leads.list`, or `leads.byCampaign` when the adapter cannot list every lead |
| `leadCollisions` | People in two or more campaigns at once, inside a tool or across tools | `leads.byCampaign` |
| `suppressionCheck` | Leads in campaigns although they are on the block list | `blocklist`, `leads.byCampaign` |
| `droppedReplies` | Replies nobody answered, longest waiting first | `replies.list` |
| `hotLeads` | Who to call first, scored from interest, replies, clicks, opens and recency | `leads.list`, or `leads.byCampaign` with a campaign given |
| `personalizationGaps` | Leads that will get broken copy because a merge variable has no value | `sequence`, `leads.byCampaign` |

"Needs" is what must be there for the insight to run at all. Many insights read more when the adapter can serve it, and say in `meta.notes` what they left out when it cannot. Each section of the reference pages lists both. The [capabilities](/docs/capabilities) page explains the keys.

## Run one by name

`runInsightByName` takes the tool name or the method name and JSON input. It is what the CLI and an agent's tool call go through. The answer's `data` is typed as JSON, so use the method when you know the insight at compile time. An unknown name throws `Invalid` and lists the known names.

`listInsights` needs no instance. It returns each insight's `name`, `key`, `description`, `needs` and its input as JSON Schema in `parameters`.

`insightTools(outbound)` returns the insights this instance can serve as agent tools, in the form every wrapper in [`outbound-sdk/tools`](/docs/tools) accepts through `extra`. Pass `only` to offer some of them.

A tool call never throws. It returns `ok: true` with `data.result`, `data.complete` and `data.notes`, or `ok: false` with an error `code` and `message`. Both carry `next`, one sentence on what to ask after this.

## From the command line

`outbound insight` with no name lists every insight as JSON. With a name it runs one and prints the answer. `--input` takes the same inputs as the method, as JSON.

```sh
outbound insight
outbound insight person_summary --input '{"person":"jane@example.com"}'
outbound insight client_report --input '{}'
```

`outbound tools`, `outbound tool` and `outbound mcp` offer the insights with the other tools, and `outbound person <email or LinkedIn URL>` runs `person_summary`. See [CLI commands](/docs/cli/commands) and [the MCP server](/docs/cli/mcp). These commands are not run by this site's tests.

## Define your own

`defineInsight` takes a name, a description, a Zod object for the input, the capabilities it needs and a `run` function. `runInsight` runs it with the same input checking, capability check and `meta` as the built-in ones, and keeps its typed answer. A definition's `execute` method is the untyped form the tool list uses.

`run` receives a context. Read through its helpers so the cost and the evidence of every read reach `meta`.

| On the context | What it does |
| --- | --- |
| `outbound` | The instance to read through. |
| `now` | The time the insight runs at, in milliseconds. Use it, not `Date.now()`, so a test can fix the clock with the `now` option of `runInsight`. |
| `rows(stats)` | Records a stats read and returns its rows. |
| `one(item)` | Records one lookup and returns the record. |
| `page(page)` | Records one page and returns its items. An unfinished page marks the answer incomplete. |
| `all(walk, cap)` | Walks a `listAll` to its end or its `max`, and marks the answer incomplete when `max` cut it short. `cap` (`{ max, what, input }`) names what was capped and the input that raises it, for the note. |
| `note(text)` | Adds a note. The same note is kept once. |
| `partial(reason)` | Marks the answer incomplete, with the reason as a note. |

The arithmetic is exported from `outbound-sdk/insights` as plain functions:

| Function | Returns |
| --- | --- |
| `rate(part, whole)` | `part / whole`, or `null` when either is unknown or the whole is zero |
| `wilson(successes, trials)` | The 95% Wilson interval as `low` and `high`, or `null` |
| `compareRates(first, second, alpha)` | The two-proportion test: `z`, `pValue`, `significant`. `null` when a side has no trials or both rates are 0 or 1 |
| `total(values)` | The known values added up. `null` when none is known |
| `mean`, `median`, `percentile(values, fraction)` | `null` for an empty list. Percentiles use linear interpolation |
| `deviation(values)` | The sample standard deviation. `null` with fewer than two values |
| `zScore(value, history)` | How many standard deviations `value` sits from the mean of `history`. `null` when the history has no spread |
| `round(value)` | Four decimal places. `null` stays `null` |
| `tally(values)` | How often each value occurs, as a `Map` in first-seen order |

`defineInsight` does not add your insight to `outbound.insights`, `listInsights` or `insightTools`. Those hold the built-in 26.

## Things to know

- **"The last N days" means N complete UTC days ending yesterday**, so a half-finished today cannot read as a drop.
- **Records are linked by exact identifier, never by name.** An email address finds a LinkedIn record only when a tool holds both for that person.
- **Finding a person costs a different number of requests on each vendor:** 1 on Instantly, 2 by profile or about 4 by email on HeyReach, and 1 to 2 on Smartlead.
- **A vendor's thread can be shorter than its sequence.** Instantly's email list does not hold every email a campaign sent, so `personSummary` counts messages sent from the lead's last step when the thread is shorter, and says so in a note.
- **A combined instance cannot read a conversation by thread id**, because a thread id is one vendor's own. `droppedReplies` reads the lead's timeline there.
- **`bounceWatch` judges a sender on everything it sent in the period**, not only in the offending campaign: no vendor reports one sender within one campaign.
- **`variantTest` makes no correction for comparing three or more variants**, and its "sends still needed" assumes both rates stay as they are.
- **`anomalies` judges a day against a flat baseline without a z-score.** If every earlier day had the same count, there is no standard deviation to measure against. A day with another count is flagged with `judgedBy: "flat_baseline"` and a `null` `zScore`, whatever `threshold` is.
- **A rate over several campaigns counts only the campaigns that report both sides of it.** `tagRollup`, `channelMix`, `periodComparison` and `clientReport` add counts up across campaigns. A campaign that reports sends but no bounces adds to the sends shown and is left out of the bounce rate, and a note says so.
- **`hotLeads` is a ranking, not a prediction.** Its score is the sum of weighted parts that are returned with it.
- **The findings are sentences built from the numbers by fixed rules.** No model writes them, so the same data always gives the same sentence.
