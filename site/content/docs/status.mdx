This page is the one place that says how far each part has been checked. Other pages link here and do not restate it.

## The package

- **Published.** On npm: `npm install outbound-sdk`. Releases from 0.2.0 on carry an npm provenance attestation; 0.1.0, published from a maintainer's machine, does not. See [installation](/docs/installation).
- **Released as 0.x.** Each version and what changed in it is in the [changelog](https://github.com/orchidautomation/outbound-sdk/blob/main/packages/outbound-sdk/CHANGELOG.md). A 0.x minor version can change what a command does by default, so read it before you upgrade.
- **Tested offline.** The test suite runs every adapter against documented vendor payloads with personal data removed, and runs every code sample on this site (see [how the samples are run](/docs/samples)).

## Adapters

| Adapter | Maturity | What that means |
| --- | --- | --- |
| Instantly | `beta` | Its reads were run, read-only, against one live workspace on 2026-11-14. |
| HeyReach | `beta` | Its reads were run, read-only, against one live workspace on 2026-11-14. |
| Smartlead | `unverified` | Untested. It has never been run against a live account. It is written from Smartlead's public documentation, which contradicts itself in places, and tested offline only. Expect mappings to be wrong until someone runs the live checks with a Smartlead key. |
| EmailBison | `unverified` | Untested. It has never been run against a live account, and no EmailBison account or key is available to the project. It is written from EmailBison's API reference, whose response examples are hand-written and often not valid JSON, and tested offline only. Its rate limit is a guess. Added in 0.5.0. Expect mappings to be wrong until someone runs the live checks with an EmailBison key. |
| In-memory | `stable` | It has no vendor behind it. |

`beta` means one workspace, once. It does not mean every plan, every account shape or every edge of the vendor's API. Both live runs fixed things the vendors' documentation got wrong or left out, so expect an `unverified` adapter to need the same. `outbound.maturity` and `outbound.caveats` report this at run time: the caveats list what each adapter assumes and has not confirmed.

No adapter is `stable`. An adapter becomes `stable` once its fixtures are captured responses and the live checks pass on a schedule.

## Insights

Run against one live workspace each on 2026-11-14: Instantly served all 26 insights the SDK had then. HeyReach served 22 and refused four as `Unsupported`: `stepFunnel`, `variantTest` and `copyReuse` (its API has no per-step stats) and `settingsAudit` (its API cannot read campaign settings). `copyPreview`, added in 0.6.0 after that run, has not been run against a live account. No insight has been run on a live Smartlead or EmailBison account.

## Rate limits

Measured on live workspaces on 2026-11-14:

- **Instantly:** 300 reads fired at once all succeeded, with no 429 and no retry (1,505 HTTP requests in 30 seconds).
- **HeyReach:** 100 reads fired at once all succeeded, with no 429 (33 seconds). HeyReach's real burst limit, 15 requests per 2 seconds, is not in its documentation; it was read from the live API's 429 response and is now declared by the adapter.
- **Smartlead:** not load-tested.
- **EmailBison:** not load-tested. Its reference documents no rate limit; the adapter assumes 3,000 requests per minute from a marketing page.
- **The Redis store** that shares one budget between processes was checked by hand against a real Redis 7 server, including two workers on one budget. It has not been run in production by anyone, nor on Valkey or Upstash.

See [rate limits](/docs/rate-limits).

## Not verified

- **The reads added after the live runs.** These follow the vendors' documentation and have not been run against a live account on any adapter: `leads.list` on HeyReach (it walks the campaigns), a reply's category and the `unread` filter on HeyReach, `stats.allCampaigns`, `campaigns.bySender`, `replies.unread`, `lists.get`, `webhooks.get`, `campaigns.progress`, `placementTests.list`, a lead's `progress` and outcome flags, and the fields `phone`, `website`, `location`, `companyLinkedinUrl`, `interestCategory`, `mailProvider`, a lead's `recipientMailProvider`, `clickedTotal` and a sender's `tags`. Their fixtures for the per-campaign stats are built from response schemas, because the references give no example.
- **Second pages on Instantly.** The live workspace was small, so for most Instantly listings only a first page was read live. Paging is tested against documented payloads.
- **Where the live numbers come from.** The live runs were made by hand on 2026-11-14 and are not reproduced by any automated job. Treat them as one observation.

- **Webhooks.** Parsing and verification are tested against each vendor's documented payloads. No parser has received a real delivery from a vendor.
- **Smartlead, end to end.** See above.
- **EmailBison, end to end.** See above. Only three of its 23 webhook events have documented payloads, and how it signs deliveries is undocumented.
- **Cloudflare Workers.** The package uses web standards outside the CLI, the exporter and the fixtures plugin, but no CI job runs it on Workers.
- **The samples on this site** run on the in-memory adapter. They prove the code runs and what the SDK does with the data given. They do not prove what a vendor's API returns.

## Confirming an adapter yourself

The repository has live checks that only read. They list campaigns and read one back, exercise each declared capability once, call every native read that needs no input, and check the rate budget.

```sh
LIVE_TESTS=1 INSTANTLY_API_KEY=... npm run test:live
```

They run only when `LIVE_TESTS=1` and the provider's key are set, and are never part of the normal test run.
